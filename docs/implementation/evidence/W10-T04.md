# W10-T04 — Zalo / sales channels / external POS by profile

Status: **blocked_external** — the provider-agnostic channel rules (venue acknowledgement, expiry, cancellation, registry, status wording) are implemented and verified locally against the sandbox channel emulator; no Zalo app, marketplace partner or external POS was chosen, so no concrete connector exists and the real profiles stay `draft`/unregistered.

## What was built

- `integrations/core/src/inbox.ts`: `channelStatus(venueAck, expired)` (plan function), `cancelled` status (the only transition allowed after `accepted`).
- `integrations/channels/src/registry.ts`: `channelConnectorFor` — a channel resolves only if its catalog profile is enabled for the runtime and a connector is registered; jobs use it instead of the W09 helper alone.
- Cloud: venue-ACK guard in the `channel.effect` job (`NO_VENUE_ACK`); idempotency key per (order, kind); `receiveChannelCancellation` + `requestChannelCancellation` + `refreshCancellation`; route `POST /v1/channels/:provider/cancellations`; migration `20261104000600_external_order_cancel.sql` (`cancelled` status, `cancel_status/code/operation_id`); the status endpoint shows `channelStatus`, `cancelStatus`, `cancelCode`.
- Domain: `ExternalOrder.Cancel` (relay-only `channel.ingest`); the order-cancel rules extracted as `cancelOrderDecision` and reused unchanged by `Order.Cancel`.
- `MiniAppBridge.tsx` (inert without a real registration), `docs/integrations/channel-acceptance.md`, rig `tests/support/channel-rig.ts` + fixture `channel-new-order.json` (emulated).
