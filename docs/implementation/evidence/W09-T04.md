# W09-T04 — Node-RED bridge and developer SDK

Status: verified_local (real route registry, local PostgreSQL 17 and **real local Supabase Auth tokens**; the venue side is the restaurant lab). No Node-RED runtime was started: the example flow is validated statically and its function nodes are executed in a VM sandbox with stubs. Nothing was run against a hosted or non-sandbox venue.

## What was built

- Role `integration` (`relay.write`, `mission.write`, `order.read`) — a service account is an ordinary Supabase user with a `venue_membership` of that role; revoking = deactivating the membership (next request `401`).
- `server/modules/automation/api.ts` and routes `/v1/automation/venues/:venueId/{commands, commands/:operationId, events}`:
  - only `Mission.Create` / `Mission.Cancel`; the caller must supply the `operationId` (so a replay is the same command); the cloud checks `relay.write` + the command's own permission, rejects at once when the venue's *applied* configuration already has the feature off (`FEATURE_DISABLED` / `FEATURE_DRAINING`, 409) and never queues it; the venue's coordinator still decides (feature, role, readiness) and its receipt is what `GET …/commands/:id` returns (own commands only);
  - cap of 50 unanswered commands per integration per venue (`RATE_LIMITED`, 429); re-sending an existing `operationId` is not counted;
  - events = polled projection of `allocation | fulfillment | mission | robot` (cursor = id, `appliedAt` = data age); any other kind is refused.
  - No route reaches a robot, MQTT topic or the database.
- `integrations/sdk/src/client.ts` (`createClient`, `submitAndResolve` — follows `pending`/`unknown` with the same id, `deliveryCapableRobots`, `readyDeliveries`, `deliveryCommand`) and `webhook-verifier.ts` (`signRequest`, `verifyRequest` over the exact bytes).
- `integrations/node-red/flows.json` + `README.md`: poll robots → remember → poll allocations → capability check + group (stable id `delivery-<session>`; no capable robot on the current map ⇒ "left for staff") → POST → pending/unknown re-checked with the same id. Credentials only from the Node-RED environment; no database/MQTT/robot node.
- `docs/integrations/developer-guide.md`: scopes, endpoints, error codes, rate limit, `/v1` evolution policy, SDK, signed webhooks, Node-RED.

## Limits

- The "SDK generator drift check" is a hand-written client plus a test that asserts the routes and the client name the same endpoints; there is no OpenAPI document or code generator yet.
- Event subscriptions are polling (≥5 s); there is no push webhook from MEKONIQ to an integrator, and no per-read audit row (the identity is on every command: `actorRef`).
- The plan's example operation id `delivery:<id>` is `delivery-<id>`: the relay accepts `A-Za-z0-9_-` only.
- Mission.Create is the only creation command exposed; creating orders, payments or settings from automation is intentionally not available. A venue's receipt arrives only when its coordinator syncs; there is no hosted-latency measurement.
