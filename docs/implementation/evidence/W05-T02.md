# W05-T02 — Table move/merge, courses and kitchen amendments

Status: verified_local (software only; SQLite lab, fixture coordinator, simulated robot, headless Chrome). No device, robot hardware, provider or Gate result is claimed. Robot behaviour is the `simulated` adapter only.

## What was built

- `Order.Amend` gained a line-cancel branch `{lineId,cancelQuantity,reason,expectedVersion}` (`orders/amendment.ts`; the add-items branch is unchanged). Cancelled quantity is taken from prepared-but-unallocated portions first, then from unprepared ones (this order is forced by the plan test: ordered 2, prepared 1, cancel 1 must raise `KitchenCancellationRequested`).
  - Unprepared part: cancelled outright, ticket/fulfillment `quantity` reduced, and a `kitchen-delta` aggregate (`KitchenDeltaCreated`, status `pending`) that the station must acknowledge with `Kitchen.AckDelta` (station-checked). A still-held (not fired) ticket creates no delta because the station never saw it.
  - Prepared-unallocated part: `KitchenCancellationRequested` creates a `kitchen-cancellation` aggregate; the portions move from `fulfillment.ready` to `fulfillment.held` (so they cannot be allocated). They leave only through the explicit `Kitchen.DisposePrepared {cancellationId,stationId,disposition: return|waste|manual,note}` (`PreparedFoodReturned` / `PreparedFoodDiscarded` / `PreparedFoodManuallyHandled`; manual needs a note). Nothing discards food automatically. `Order.Cancel` (held > 0 -> `REQUIRES_DISPOSITION`) and `Bill.Close` (`DISPOSITION_PENDING`) refuse while a request is open.
  - Allocated, served or returned portions cannot be cancelled (`FULFILLMENT_ACTIVE`); `CANCEL_EXCEEDS_ORDER`, `REASON_REQUIRED`, `INVALID_QUANTITY`, `VERSION_CONFLICT`/`VERSION_REQUIRED` (order version), `ORDER_FROZEN` once billed. The line keeps its original `quantity`, priced snapshot (`charges`, `totalMinor`, ...), and gains `cancelledQuantity`, `cancelled{subtotalMinor,discountMinor,serviceMinor,taxMinor,taxIncludedMinor,totalMinor}` and an append-only `cancellations[]`. A fully cancelled order becomes `cancelled`.
  - Money: the cancelled amount of each component is its snapshot share for the cumulative cancelled units, computed with `allocateMinor` over two buckets (round half up, so cumulative shares are monotone and the full cancel equals the line exactly); the cancelled total follows the quote identity `subtotal - discount + service + tax`. `summarize()` subtracts `line.cancelled`, so order `totalMinor`/`summary` and prepared bills reflect it. Never re-priced from the current menu (a unit test sweeps inclusive/exclusive tax, both discount orders and tiny/odd prices).
- Courses (`orders/course.ts`): an item in `Order.Place`/`Order.Amend` may carry `course` 1..9 (default 1, `INVALID_COURSE` otherwise); lines of course >= 2 get a `held` kitchen ticket (not acceptable/readyable). `Order.SendCourse {orderId,course,action: fire|hold,expectedVersion}` fires held tickets (`CourseFired`) or re-holds not-yet-accepted ones (`CourseHeld`), recording `order.courses`. Each ticket stays on its own station, so kitchen and bar partial-ready are independent.
- `Session.Move {sessionId,toTableId,expectedVersion}` (`orders/move-table.ts`): open, un-frozen session to a free table; session `tableId` + `tableHistory`, both tables' `activeSessionId`, open orders' `tableId`, and `session.revision` +1 (so W05-T05 can bind guest tokens to it). Rejects `SAME_TABLE`, `TABLE_OCCUPIED`, `SESSION_FROZEN`, `SESSION_CLOSED`.
- `Session.Merge {sourceSessionId,targetSessionId,expectedSourceVersion,expectedTargetVersion}` (`orders/merge-session.ts`): `SAME_SESSION`; both sessions version-checked in sorted-id order; `GRANT_UNRECONCILED` when any bill of either session has a grant whose status is not `reconciled`; `SESSION_FROZEN` when either has a prepared bill. Source orders, kitchen tickets, fulfillment, allocations, deltas and cancellations are re-pointed to the target (keeping `originSessionId`); the source session stays as history (`status merged`, `mergedInto`, order refs intact) and its table is released; both sessions' `revision` +1. No bill is rewritten or deleted (a seeded bill and grant are asserted untouched).
- Robot missions (`fleet/retarget.ts`, used by move and merge): an unfinished hand-off stop for the moved allocations is pointed at the new table id (which is also the robot binding key, so renaming a table changes nothing). A stop the robot is driving to or waiting at gets a new robot command under `revision + 1` (`MissionRetargeted`, `RobotGoalRetargeted`, old command `superseded`, `robot.cancel` for the live old goal queued before the new `robot.execute`); a late `Mission.ConfirmStop` for the old revision is `STALE_STOP` and old-command events are `STALE_ROBOT_EVENT`. A queued mission is retargeted in place. A `needs_attention` mission blocks the move (`MISSION_UNRESOLVED`); an unbound new table gives `TARGET_UNBOUND`.
- Registry/permissions/features: `Session.Move`, `Session.Merge`, `Order.SendCourse` -> `order.write`; `Kitchen.AckDelta`, `Kitchen.DisposePrepared` -> `kitchen.write` (station-scoped like the other `Kitchen.*`); features `sessions`/`pos.order`/`kitchen` as `finish_existing`. `Session.Open` now stores `revision: 0`.
- UI: `Pos.ts` has an "Open tables" panel (move to a free table, merge into another open table, cancel an item with quantity and reason, fire a held course). Drafts live outside the render; on `VERSION_CONFLICT` the screen refreshes, keeps the unsent quantity/reason and shows "a newer version (vN) was written by another device". `Kitchen.ts` shows delta tickets with Acknowledge, cooked-food cancellation requests with Return / Waste / Handled manually (+ note), course headings and held tickets without actions. The LAN role filter (`LanService.kt`) and the fixture coordinator now include `kitchen-delta` and `kitchen-cancellation` for kitchen roles.
- Test fixture: `lab.seed('order-line', lineId, {ordered,prepared,allocated,served,version,itemId?,tableId?,sessionId?,orderId?,course?})` in `tests/support/restaurant-lab.ts` expands into table + session + one order (priced by the production `quoteOrder` from the fixture menu) + kitchen-ticket + fulfillment. `version` is the order's version (what `Order.Amend.expectedVersion` targets); other aggregates start at 1; `fulfillment.ready = prepared - served`.

## Limits

- Prepared-first cancellation order is a policy forced by the plan test; there is no payload switch to cancel the unprepared portions first. The kitchen then decides the cooked portions' fate, so food is never lost silently.
- A delta ticket does not block billing or closing (only an open cooked-food cancellation does); a station that never acknowledges is a visible pending record, not a payment blocker.
- Merge and move refuse sessions with a prepared bill (`SESSION_FROZEN`); there is no bill reopen/transfer here (W05-T03/T04). `GRANT_UNRECONCILED` is checked first, so a frozen session with an open grant reports that code.
- Retarget re-aims only hand-off stops; load stops (stations) are untouched. The stop's allocations are assumed to belong to one table. The cancel of the old goal is an effect for the simulated adapter; real-robot supersede semantics are W06 and are not claimed. A `needs_attention` mission blocks the move until reconciled.
- Guest-token rotation on session close/new guests is W05-T05; this task only maintains `session.revision` (bumped on move, merge) and does not add `Session.Close`.
- Android: `LanService.kt` visibility set edited (adds two kinds); Kotlin tests were not run (no device/emulator). The Capacitor/Android web bundle was not rebuilt.
- The order-line fixture is one line per order; multi-line fixtures are built through `Order.Place`.
