## What was built

- Shifts and cashbook (`packages/domain/src/cash/{shift,cashbook,ledger}.ts`, `basic-shift.ts` renamed to `shift.ts`, `Shift.Open` unchanged):
  - `shiftLedger` / `expectedCash` (`ledger.ts`, pure, also used by the tablet UI): expected cash = opening + cash receipts (tendered) + cash-in − cash-out − cash refunds − change, recomputed from ledger facts: captured cash `payment`s of the shift (`tenderedMinor`, `changeMinor`), cash `refund`s that left that shift's drawer, and `cash-movement`s. The running `shift.cashMinor` counter is **not** used for the result; `Shift.Close` stores `counterDriftMinor = cashMinor − (receipts − change)` for audit, so a drifting counter is visible, never authoritative.
  - `Shift.Close {shiftId,expectedVersion,countedMinor,approve?,reason?,note?}`: records counted cash, expected, variance (signed), the ledger breakdown, `closedBy`, `approvedBy`, `varianceReason`. A non-zero variance needs `approve:true` (permission `shift.approve`, manager/owner) plus a reason, and the approver cannot be the shift's own cashier (`SELF_APPROVAL_FORBIDDEN`, e.g. a manager's own shift is approved by the owner). Another cashier's shift can only be closed with `approve:true`. A closed shift is immutable: `SHIFT_CLOSED` on re-close, cash payment (`ACTIVE_SHIFT_REQUIRED`), movement. Closing also closes the cashier's `cashier-shift` so a new shift can be opened.
  - `Cash.RecordMovement {shiftId,direction:in|out,amountMinor,reason,adjustment?,approve?}`: float top-up/payout in an open shift by its own cashier (`SHIFT_NOT_OWNED` otherwise; `approve` = manager); cash-out cannot exceed expected cash (`INSUFFICIENT_CASH`). **Reopened-day adjustment**: after close, `adjustment:true` (manager, `shift.approve`, reason) writes a separate `cash-movement` (`adjustment`, `afterClose`) and leaves the closed shift snapshot byte-identical; `shiftLedger` reports it as `adjustmentMinor` beside the closed totals.
  - Authority: `requiredPermissions` (`application.ts`) adds `shift.approve` when the payload carries `approve:true` or `adjustment:true` for `Shift.Close`/`Cash.RecordMovement`; the handlers enforce ownership. Role grants (`rbac.ts`): manager `shift.approve`, `print`; cashier `print`; new role `spooler` (`print.observe`) for the device spool; owner `*`.
- Printing (`integrations/printing/src/{profile,receipt,escpos,spool}.ts`, `packages/domain/src/printing/print.ts`):
  - `Print.Request {billId,printerId?}` queues one `printer.send` effect (receipt of a closed bill, provisional "TAM TINH" for a prepared one) and creates a `print-job` holding the issued receipt model and the attempt list. The bill is never touched (`bill.status` unchanged). A second original for the same bill+kind is `ALREADY_PRINTED` unless every earlier attempt failed (nothing was ever sent).
  - States: `pending` (effect pending) → `sent` (effect `dispatching`: claimed, bytes in flight) → `unknown` | `confirmed` | `failed` (nothing sent). Transport result: printer acknowledgement → confirmed; bytes written but no ack, timeout, any send error, or a crash while `dispatching` → **unknown**; `PrinterNotReached` (known nothing left the device) or an unusable printer profile → failed. **Unknown is never retried automatically**: `dispatchPrintEffects` only touches `pending` effects (claim → attempt, `attempts` increments → `completeEffect`), exactly one send per effect.
  - `Print.ConfirmReprint {jobId,reason,printerId?}`: the user's decision creates a NEW attempt/effect flagged `reprint` (`reprintNumber`, reason, actor, time in the job) and the ESC/POS output carries `*** IN LAI / REPRINT #n ***` at top and bottom. Refused while the previous attempt is still pending (`ATTEMPT_IN_FLIGHT`); the reprint reuses the issued receipt, not a re-priced bill.
  - `Print.Observe {jobId,effectId,status,code?}` (permission `print.observe`, `spooler` role) records the spool outcome on the job so the UI and reconciliation see it; idempotent per attempt/status. It is only accepted when the device's own spool runner hands the handler the outbox's record of that effect (read-only `spool-effect` snapshots from `spoolEffectSnapshots`, read from the runner's own store right before it submits) and the claimed status equals the stored effect status (`EFFECT_STATE_UNAVAILABLE` / `EFFECT_STATUS_MISMATCH` otherwise). Handlers cannot read the outbox themselves, so the runner supplies it; a forged `failed` (which would license an unmarked duplicate original) from the API, relay or any role including owner is rejected.
  - Repair: every `dispatchPrintEffects` run first re-reports (idempotent Observe, code `OBSERVATION_RECOVERED`) each `printer.send` effect that is final in the outbox while its job attempt is still `pending` (crash/failure between `completeEffect` and Print.Observe). Nothing is sent again. `onOutcome` failures are no longer mistaken for send errors.
  - `Print.Resolve {jobId,effectId,outcome:'printed'|'not_printed',reason}` (permission `print.resolve`, manager/owner; `note()` reason required): reconciliation of an `unknown` attempt after the paper is checked; sends nothing. `printed` closes the attempt as confirmed by staff (`source:'staff'`); `not_printed` keeps it unknown with the resolution recorded and job status `not_printed`. A fresh *original* is deliberately NOT allowed after `not_printed` (a stalled printer may still print the old job when paper is reloaded, which would produce an unmarked duplicate), so it only unlocks `Print.ConfirmReprint`, which stays marked. `ConfirmReprint` on an unresolved unknown attempt is `UNKNOWN_UNRESOLVED`: unknown goes to reconciliation, and nothing retries by itself.
  - Printer readiness (`policy/readiness.ts`, `integrations/printing/src/profile.ts printerSupport`): `printer` readiness is true only when an installed `printer` snapshot passes `printerSupport` (status installed, model, ESC/POS profile, 24..64 columns, validation `fixture|venue_approved`; transport `network`; `usb` only when `venue_approved`; `bluetooth` and others never). It was a constant `false` before. The `printing` feature maps `Print.Request`/`ConfirmReprint` as `new` (needs `NOT_READY`-free + enabled) and `Print.Observe` as `finish_existing`.
  - `receipt.ts` builds the model from the bill's frozen lines and charges (W05-T01) and the bill's payments/change/refunds (W05-T03); money stays integer strings. `escpos.ts` renders ESC @, alignment, bold, double size, feed, cut (`GS V B 0`); text is folded to ASCII (Vietnamese code pages are printer-specific and unverified).
  - KDS/sales independence: the printing guard only applies to `Print.*`; the readiness test breaks every printer profile and a chef still accepts a kitchen ticket.
- Test lab: `tests/fixtures/restaurant-v1.json` enables `printing` and adds a clearly-labelled **FIXTURE spool printer** profile (`validation:'fixture'`, `network`, label "FIXTURE spool printer (software only, not a physical printer)"). `createRestaurantLab` seeds it, and runs the real `dispatchPrintEffects` over the coordinator outbox after each `Print.Request`/`Print.ConfirmReprint` with an injected fixture transport: `lab.fault('printer-timeout')` (transport hangs, the spool's timeout fires), `'printer-ack-lost'` (bytes recorded in `lab.printed`, no ack), `'printer-unreachable'` (`PrinterNotReached`). `lab.runSpool()`, `lab.printed`, `lab.autoSpool` are exposed; actors `printer-spool` and `cashier-2` added.
- UI: `apps/tablet-web/src/screens/CashShift.ts` (open with float, ledger breakdown, expected cash, cash in/out, count and close with manager-approval path, closed-shift summary and post-close adjustment) and `PrintQueue.ts` (printer profile with support/unsupported reason and fixture warning, print button, per-attempt states, unknown warning, reprint with required reason), routes `/cash` and `/print`, nav links, VI/EN strings. `LanService.kt` now lets billing roles see `cash-movement`, `print-job`, `printer`.
- Golden bytes: `tests/fixtures/printing/receipt-cash-change.json` with `.42col.hex`, `.32col.hex`, `.42col.reprint1.hex`.

## Limits

- No physical printer: the transport is a fixture. Network/USB socket transports on Android, the real printer's ack behaviour (most raw ESC/POS printers do not acknowledge, so real jobs will mostly end `unknown` until a status read-back is verified), Vietnamese code pages (output is ASCII-folded) and USB `venue_approved` validation are W11 gate items. `blocked_external` is not set for this task because the task's exit is software; the physical print gate stays in W11-T05.
- Nothing in the app calls `dispatchPrintEffects` yet outside the lab: there is no native print transport, so on a real tablet jobs stay `pending` (a printer profile cannot be installed without hardware, so `printing` cannot be enabled by readiness). The tablet runtime wiring (like `robot-runtime.ts`) arrives with the native transport in W11.
- Print.Observe's outbox record is supplied by the in-process runner (`spoolEffectSnapshots`); the tablet runtime that does this arrives with the native transport (W11). The lab does the same.
- Cash in/out and close are by the shift's own cashier or a manager with `shift.approve`; the physical cash count itself is typed in (no cash-drawer hardware). Cash refunds against a payment whose shift is already closed land on the actor's open shift (existing W05-T03 rule). Settlement-grant cash (offline) is not yet a shift receipt.
- Android: `LanService.kt` visibility set edited, Kotlin tests not run (no device/emulator), web bundle not rebuilt. The e2e for the new screens is read-only (the shared fixture coordinator is used by later specs); mutating UI flows are covered by the command-level integration tests.
