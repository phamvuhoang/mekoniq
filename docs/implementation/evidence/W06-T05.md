# W06-T05: Commission S100/ZLTECH profiles and safety boundary

Commit: `docs: define measurable robot commissioning and vendor profiles` (`git log --grep 'measurable robot commissioning'`).

Status: **blocked_external** for the hardware part; the software part (schemas, validator, read-only CLI, docs) is verified locally.

**Nothing was measured on hardware.** No robot, onboard computer, serial/CAN/RS485 bus, supplier SDK or firmware was available or touched, and no active motion was run. **No safety certification is claimed.** Simulation (Gazebo, `geometry_sim.yaml`) never proves load or safety. The fixtures contain synthetic `TEST-ONLY` values and throwaway test keys; a pass proves the validator's rules, nothing about any robot.

## What was built

- `robotics/hardware/profiles/{wheeltec-s100,zltech-differential}.schema.json`: draft-07 schemas defining each field with units and constraints. Vendor model/firmware, `/odom` `/scan` `/tf` evidence, encoder unit, watchdog independence, control-bus register map (entries need a cited source document), geometry (same keys as `geometry_hardware.template.yaml`), supervised E-stop/bumper/cliff evidence, tested payload, verified capabilities, venue acceptance, `RobotManifest`, ES256 signature.
- `robotics/hardware/profiles/*.instance.json`: the real profile instances. Every vendor-specific value is `null`, with `vendor.blocked_external` naming what is missing. No register address, baud rate, wheel size, speed or mass was entered.
- `tests/hardware/commissioning.py`: `validate_commissioning(record, target_payload_kg, capability, commissioning_key)` returning `status` on the shared ladder plus reason codes, and a CLI.
  - Plan's `deployment_status` is used verbatim. `safety_verified` covers vendor identity, measured non-illustrative geometry (null/absent = unmeasured), topics, encoder unit, independent watchdog, E-stop independent of software, E-stop/bumper/cliff passes, safety firmware == vendor firmware, manifest validity and verified capabilities. `payload_verified` needs `tested_payload_kg >= target` and the manifest rated load (grams) >= target.
  - The manifest is validated against the shared `packages/contracts` `RobotManifest` (the schema file is read from the repo, never copied). Level names equal `robot-manifest.schema.json` and T01's `profileReason` ladder.
  - `hardware_validated`/`venue_approved` need a valid ES256 signature over the RFC 8785 canonical JSON of the record without `signature`, checked with `mekoniq_agent.protocol.verify_es256` (T03; no second crypto implementation) against a provided public JWK whose `kid` equals `signature.keyId`. Unsigned, key missing, tampered, wrong key or wrong key id cap the status at `integration_tested` and mark the manifest not accepted. Venue acceptance is inside the signed body.
  - A manifest claiming more than the evidence supports gets `CLAIM_EXCEEDS_EVIDENCE`. Unsupported/unverified capabilities, an unknown profile (household vacuum) and a rated load below the target each have their own code.
  - CLI is read-only (`validate`). `active-motion` refuses with `ACTIVE_MOTION_CONFIG_MISSING` unless `target`, `observer` and `test_area` are passed at execution, and even then stops with `VENDOR_INTERFACE_NOT_PROVIDED`. No network or device I/O exists in the module.
- `docs/operations/{robot-commissioning,safety-handoff}.md`: levels, procedure, and the boundary: software only requests STOP, hardware reset comes from the controller, no software reset.
- `tests/fixtures/hardware/`: `commissioning-complete.json` (synthetic), signed hardware_validated and venue_approved samples, two public JWKs (test and wrong key), and `generate-signed.mjs` (throwaway keypair per run; private keys are never written).

## Limits and external blockers (`blocked_external`)

- Supplier SDK/firmware/pinout and CAN/RS485 register maps for WHEELTEC S100 and ZLTECH are not in the repo; the profile schemas carry fields and constraints only, and the two chassis share one field set because no vendor-specific differences are known.
- No physical measurements (dimensions, mass, speeds, braking/turn, rated and tested load, stop distances) and no supervised E-stop/bumper/cliff/watchdog tests. Until then both profiles are `integration_tested` and not dispatchable (T01).
- The commissioning signing key and its custody are outside this repo; only verification exists. Test keys must never be trusted in production.
- The `active-motion` suite has no vendor driver; its motion body is deliberately absent.
- `.github/workflows/ci.yml` is untouched; the pytest step for `tests/hardware` is left to the final fix wave.

## Fix round 1 (fail-closed hardening)

- A NaN, infinite, non-positive, boolean or non-numeric `target_payload_kg` is `TARGET_PAYLOAD_MISSING` (status stays `integration_tested`, manifest not accepted). The CLI rejects such `--target-payload-kg` values at parse time (exit 2, `TARGET_PAYLOAD_INVALID`).
- New reason codes keep a record at `integration_tested`: `VENDOR_BLOCKED_EXTERNAL` (non-null `vendor.blocked_external`), `VENDOR_UNSOURCED` (null `vendor.source`), `ENCODER_UNSOURCED` (null `interfaces.encoder.source`), `CONTROL_BUS_UNSPECIFIED` (null `control_bus.kind`).
- The synthetic TEST-ONLY fixture now sets `control_bus.kind` to `"can"` (no registers); keys and signed samples were regenerated with a fresh throwaway keypair (public keys only committed).
- `CAPABILITY_UNVERIFIED` is reported once (duplicate check removed).
- Plan steps 3 and 5 are annotated "software part only; hardware blocked_external".
- Result: `.venv/bin/python -m pytest tests/hardware -q` -> 25 passed.
