## What was built

- `robotics/agent/mekoniq_agent/nav2_adapter.py`: `Nav2Navigation`, the W06-T03 `NativeNavigation` port over `nav2_msgs/action/NavigateToPose`. Pure Python, with the action client injected.
  - Completed only when the goal was accepted, the terminal status is SUCCEEDED and `result.error_code == 0`.
    - Rejected goals raise `NativeRejected("NAV2_GOAL_REJECTED")` and report `rejected`.
    - ABORTED, CANCELED, UNKNOWN and any unrecognised status code never complete.
    - SUCCEEDED with a non-zero `error_code` is `failed`.
    - SUCCEEDED with no retrievable `error_code` is `unknown`, not completed.
  - A cancel or STOP request returns the server's acknowledgement only. The goal is canceled when a later status read says CANCELED (`canceling` until then).
  - The executor's goal UUID is the ROS `goal_id`. `query(uuid)` asks the action server about that UUID, so a restarted agent can re-attach. An unlisted goal returns `not_found` (the executor keeps it `unknown`, never resends). A client error propagates (the executor marks it unreachable).
  - Localization readiness gates `start`, with the reason as the refusal:
    - `LIFECYCLE_NOT_ACTIVE:<node>`, `LOCALIZATION_UNAVAILABLE` (no pose, NaN, or negative covariance beyond float noise), `FRAME_MISMATCH`, `MAP_MISMATCH` (id or revision), `COVARIANCE_TOO_LARGE`.
    - A probe failure is a refusal with nothing sent.
  - Target checks: goal frame equals the bound map frame, map id and revision match, finite x/y/yaw. Units are metres, radians and m/s. `yaw_to_quaternion` / `quaternion_to_yaw` are planar and tested (round trip, known values, wrapping).
  - Speed limit (`RobotCommand.limits.speedLimitMps`) is carried or refused, never ignored:
    - The client publishes `nav2_msgs/SpeedLimit` (m/s). It is global to the controller, so `0.0` (Nav2's "no limit") is published when a goal has none, and a previous goal's limit never leaks.
    - Delivery failure raises `NativeRejected("SPEED_LIMIT_NOT_APPLIED")` with no goal sent.
    - `supports_speed_limit` comes from the client, so the executor's existing `SPEED_UNSUPPORTED` rule applies unchanged.
  - `Nav2Config`: namespace per robot profile (`/robot_1/navigate_to_pose`), explicit `map`/`odom`/`base_link` frames, and covariance bounds. The defaults are simulation-illustrative; `Nav2Config.for_profile(profile, namespace)` binds map id, revision and frame to the provisioned `Profile`.
- `robotics/agent/mekoniq_agent/nav2_rclpy.py`: the rclpy client. ROS imports are lazy, so nothing needs ROS to import it.
  - It sends goals with the executor UUID as `goal_id`.
  - It reads the server's `_action/status` topic and `_action/get_result` for the `error_code` of terminal goals.
  - It cancels through the `_action/cancel_goal` service by UUID (the zero UUID cancels all), not by a handle that does not survive a restart.
  - Localization comes from the lifecycle `get_state` services, `amcl_pose` (covariance x, y and yaw) and the map identity.
  - Map identity is read from `<map>.identity.json` beside the map yaml that `map_server` reports as loaded.
- `robotics/agent/tests/support/{fake_action_client,fixtures}.py`: fakes and fixtures. The fakes keep goals in the client, like an action server that outlives the agent.
- `robotics/navigation/{launch,config,maps}` (package `mekoniq_navigation`):
  - `navigation.launch.py` has an explicit node list: `map_server`, `amcl`, `controller_server`, `smoother_server`, `planner_server`, `behavior_server`, `bt_navigator`, `velocity_smoother`, `collision_monitor`, plus two lifecycle managers.
  - Single `cmd_vel` source: `controller_server`, `behavior_server` -> `cmd_vel_nav` -> `velocity_smoother` -> `cmd_vel_smoothed` -> `collision_monitor` -> `cmd_vel`. There is no `twist_mux`, and the platform never publishes motor commands. A test asserts the remaps and that the agent's only publisher is `SpeedLimit`.
  - The explicit list was chosen over `nav2_bringup`'s `navigation_launch.py`: Jazzy 1.3.13's list also starts `route_server` and `docking_server`, which this task does not use.
  - `config/nav2_params.yaml` is the Jazzy parameter set (AMCL, RPP controller, NavFn planner, costmaps, velocity smoother, collision monitor). Its tuning is simulation-illustrative.
  - `maps/` holds the generated occupancy map and `restaurant_sim.identity.json` (map id `map-a`, revision `r1`, waypoints).
- `robotics/description/{urdf,config}` (package `mekoniq_description`): `restaurant_robot.urdf.xacro`, a differential-drive robot with the Gazebo DiffDrive, JointStatePublisher and gpu_lidar plugins.
  - `geometry_sim.yaml` is marked `illustrative: true`.
  - `geometry_hardware.template.yaml` ships every measured value `null` (hardware needs measured values from W06-T05). A test checks the template keys match the sim keys and the xacro defaults equal the sim numbers.
- `robotics/simulation/{worlds,launch,tests}` (package `mekoniq_simulation`):
  - `worlds/generate_restaurant.py` is the single source for `restaurant.sdf` and the Nav2 map. A test fails on drift. Layout: kitchen, a 1.0 m wide corridor as the only route, a dining room, four tables, a walking obstacle (`/model/walker/cmd_vel`) and a parked blocker moved with the `set_pose` service.
  - `launch/restaurant_sim.launch.py` starts headless `gz sim -s --headless-rendering`, robot_state_publisher, the robot spawn, the `ros_gz_bridge` and Nav2 under namespace `robot_1`.

Findings from bringing it up (all fixed in the committed assets):

- The chassis collision box was initially below the ground plane. The robot's wheels spun and odometry advanced while Gazebo showed it had not moved; only the ground-truth check caught this.
- A goal accepted by this process is bridged by its goal handle only until the status topic lists it (or 10 s), then the handle is dropped. A Nav2 that restarts and forgets the goal gives `not_found`, not a stale `executing` (unit-tested with a fake handle and clock).
- **Costmap scan topic (fix round 1).** The costmap obstacle layers resolve a relative `scan` against their own sub-node namespace (`/robot_1/local_costmap/scan`), where nothing publishes. Under a namespace both costmaps were therefore blind to the lidar: only the collision monitor reacted, and the first-round "obstacle/replan/blocked" results passed without planning around anything. The earlier centre-distance assertion (> 0.35 m) could not have caught this. `navigation.launch.py` now rewrites every observation-source `topic` to the absolute `/<namespace>/scan`; a static test pins it.
- With the layers working, the first footprint-clearance runs showed contact: the robot's rectangular footprint clipped a blocker on turns and stopped 0 to 0.02 m from it. The costmaps now use `robot_radius` 0.375 m (the chassis' circumscribed radius) with `inflation_radius` 0.65 m. Clearance is 0.17 m or more in the final runs.
- AMCL defaults produced covariance above the readiness bound. After tuning it runs about 0.005 to 0.02 m^2 and about 0.01 rad^2. The bounds (0.09 m^2 and 0.10 rad^2) remain simulation-illustrative.
- Real-time starvation on a shared host dropped lifecycle bonds and aborted goals. The lifecycle managers now use `bond_timeout` 10 s and `bt_navigator.default_server_timeout` is 1000 ms.
- `RclpyActionClient.cancel_all` was checked against real Nav2: with nothing active it returns `ERROR_NONE` (0); a cancel for an unknown goal id returns 2 (`UNKNOWN_GOAL_ID`). Code 1 is `ERROR_REJECTED`. A rejected cancel-all is acknowledged only when a status list was received and shows nothing active; "no status received yet" (observed on an idle server before any goal) is not idle (unit-tested).

Plan-test deviation: the plan's test calls `adapter.start(goal_fixture())`. The W06-T03 `NativeNavigation.start(goal_uuid, target, speed_limit_mps)` port takes three arguments, so the test calls `adapter.start(**goal_fixture())` where `goal_fixture()` returns those keyword arguments, and `poll()` is kept for the plan's single-goal view.

## Limits

- Simulation evidence only: illustrative world and geometry, headless software rendering, one host. It says nothing about a real robot's localization, payload, braking, safety rating, or VDA/vendor compatibility.
- Flakiness: on this shared host (other agents and containers competing for the Docker VM) roughly one full run in four failed a scenario before the fixes above (a non-completing goal, a lifecycle bond loss under CPU starvation, once a startup race with `map_server`). After the final assets the last 5 full runs passed 9/9. Treat the gate as "passes on an idle machine", not as a reliability claim.
- Clearance is sampled from ground truth at about 60 Hz with a 0.02 m margin; a pass means no contact in the sampled poses, not a safety distance. The collision monitor's `approach` polygon slows the robot asymptotically; the scenarios do not show a guaranteed stopping distance.
- The first-round development runs used an interactive container with the same apt packages; the fix-round runs use the image built from the committed `robotics/simulation/Dockerfile` (local image id above, base `ros@sha256:8eed0a4669bbf43ee331878a4c39bd8ebddea8e3312a58b4fae8edb14526b617`, 3.5 GB). The image id is a local build id, not a registry digest, and the apt layer follows the Ubuntu/ROS archives, so a rebuild at another date may pick newer package versions.
- `RclpyActionClient` finds a terminal goal's `error_code` through `get_result`, which the action server keeps only for its result-retention window. After that window the goal is unlisted and the adapter answers `not_found` (the executor keeps it `unknown`). An empty/late-latched status topic is treated as "no goals" after a 3 s wait, so slow DDS discovery can only produce `not_found`, never a guessed outcome.
- `request_stop` cancels every Nav2 goal. It is not a physical stop; the robot's own motor/E-stop layer is W06-T05.
- AMCL covariance is a particle-filter estimate and the bound is a readiness gate, not a safety guarantee. A loss of localization during a goal is left to Nav2 (it aborts); the adapter gates only `start`.
- Hardware/pilot gates remain for W06-T05/T06: measured geometry, the S100/ZLTECH profiles, hardware commissioning, and Gate B.
