# W08-T01 — Promotions, vouchers and usage limits

Status: verified_local (software only; SQLite restaurant lab + Postgres-backed cloud relay test). No external coupon provider, no multi-venue authority service is exercised.

## What was built

- `packages/domain/src/promotions/`:
  - `rules.ts` `Promotion.Publish` — a promotion is data (no uploaded code): percent/fixed (the existing coupon shape, so the existing allocator applies it), item list, venue-time window (inclusive business dates, weekdays, minutes of the day), channels, customers, venues, `priority`, `exclusionGroup`, `stackable`, `requiresVoucher`, `status active|retired`; re-publishing bumps `revision` (orders already priced keep their frozen charge snapshot). `ineligible(rule, ctx)` is pure and shared by pricing and the tablet. `rangesOverlap` (plan function) lives here for the booking code to reuse in W08-T03.
  - `stacking.ts` `selectPromotions` / `resolvePromotions`: requested ids → deterministic coupon list (priority desc, id asc); explicit refusals `PROMOTION_INACTIVE`, `PROMOTION_NOT_ELIGIBLE`, `PROMOTION_EXCLUDED` (same exclusion group, or a non-stackable promotion beside another), `PROMOTION_REQUIRES_VOUCHER`, `VOUCHER_NOT_HELD`. Caps come from the existing allocator (each coupon takes from what the earlier ones left), so a stack can never drive a line negative.
  - `voucher.ts` `Voucher.Issue` (limit, scope = this venue or `shared`, per-customer limit, validity as **venue business dates**, `restoreOnRefund` policy) and `Voucher.GrantEscrow` (moves uses from the shared pool into one venue's exclusive allocation with a revision).
  - `redemption.ts` `Voucher.Reserve` / `Voucher.Redeem` / `Voucher.Release`: one use per voucher+ref; a retried reservation/redemption is a no-op; the last use is won by exactly one of two concurrent redemptions (store version check — the plan's `UPDATE … WHERE remaining > 0` equivalent). A hold is **never released by time** (unknown payment keeps it); `Redeem{reservedRef}` converts the hold without taking a second use. A redeemed use returns only through `Release{reversalSource}`: the refund must exist (`REFUND_NOT_FOUND`), the use's snapshot policy must allow it (`RESTORE_NOT_ALLOWED`), one refund restores it once, a different refund is `ALREADY_REVERSED`. The redemption snapshots the bill's frozen discount charges for the voucher's promotion when the bill exists.
  - Shared vouchers: spendable only through an exclusive allocation for this venue, else `SHARED_VOUCHER_OFFLINE_DENIED` (never "ignore the limit"); a stale `grantRevision` is `STALE_GRANT`; another venue's voucher is `VOUCHER_SCOPE_DENIED`.
- Pricing: `quoteForCommand` resolves promotion ids placed in the normal `discountIds` list (so `Catalog.Quote`, `Order.Place`, `Order.Amend` all price them; `discount.apply` is still required, the `promotion` feature too) into ordinary coupons — one mechanism, one frozen `charges` snapshot.
- Permissions: `promotion.write` (publish, issue, allocate — manager), `voucher.redeem` (cashier, manager). Feature `promotion`.
- Cloud (`apps/cloud-web`): generic back-office relay — `POST /v1/venues/:venueId/commands` (allowlist `cloudCommandTypes`, per-command permission via `requiredPermissions`, relays a pending intent to the venue owner; the cloud writes no domain state) and `GET /v1/venues/:venueId/records/:kind` (projection read, per-kind permission). Page `/admin/promotions` (`Promotions.tsx`, shows "sent, awaiting acceptance" rather than "applied"). W08-T02/T03 extend the same allowlists.
- Tablet: `PromotionStatus.ts` at `/promotions` (rules/quota from the tablet's cached snapshots, offline-capable; warns when a shared voucher has no allocation; redeem form). `LanService.kt` lets cashier/kitchen read `promotion`, `voucher`, `voucher-use`.

## Limits

- The check that a voucher-gated promotion is covered by a live hold happens at pricing, but the use itself is taken at `Voucher.Reserve`/`Redeem` — a cashier must reserve before pricing; there is no automatic reservation inside `Order.Place`, and `Order.Amend` does not release a hold when the discount is removed (the cashier releases it).
- Shared-pool vouchers are only as exclusive as the allocation: the allocation command (`GrantEscrow`) must run where the pool lives (cloud/authority). In the lab one store plays both roles; the cross-venue transport of an allocation to a tablet is the W04/W02 grant path and is not re-proven here. No online redemption path for the shared pool exists yet (offline-or-allocated only).
- Promotion windows support one time-of-day range per promotion (no overnight range; use two promotions).
- Cloud UI is a form over the relay; it was type-checked/built, not browser-tested.
