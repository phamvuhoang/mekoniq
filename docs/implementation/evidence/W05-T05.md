## What was built

- Guest token (`packages/domain/src/service/guest-token.ts`):
  - `Guest.IssueToken {sessionId,channel:'qr'|'kiosk',ttlMs?}` (staff, `order.write`; 1 min..24 h, default 12 h on the trusted coordinator clock). The capability `{schemaVersion,id,organizationId,venueId,sessionId,tableId,revision,channel,issuerDeviceId,issuerDeviceEpoch,issuerEpoch,issuedAt,expiresAt,expiresAtMs}` is signed by the **coordinator store at commit** with the coordinator key, exactly like settlement grants (`sql-store.ts`; Kotlin twin in `JournalDatabase.kt`). A `guest-token` aggregate can only be created by `Guest.IssueToken` and never rewritten (`INVALID_GUEST_TOKEN_MUTATION`). It is not a Supabase JWT and carries no permissions.
  - Guest wire token = base64url(JSON(capability + signature)); `encodeGuestToken`/`decodeGuestToken`.
  - `guestCommand(token,type,payload)` is the one builder used by the cloud guest API and the lab: only `Order.Place`→`Guest.PlaceOrder` (`items`,`menuVersion`), `Guest.CallStaff` (`reason`), `Guest.RequestBill`, `Guest.ReportIssue` (`category`,`note`) pass; every other type is `GUEST_COMMAND_FORBIDDEN`; session/table/robot ids and coupons are dropped.
  - `guestContext` (venue side, every guest command): signature against the `__scope__` authority key, issuer = current owner device/epoch/coordinator epoch, stored token with the same signature, expiry on the trusted clock (`GUEST_TOKEN_EXPIRED`), then `guestSessionValid` (plan snippet, verbatim) + table match → otherwise `SESSION_EXPIRED`. Tokenless guest commands are accepted only from a device paired by `Robot.PairDisplay` while its robot waits (`awaiting_action`) at a table with an open session (`ROBOT_NOT_AT_TABLE` / `GUEST_TOKEN_REQUIRED`).
  - `Guest.PlaceOrder` reuses the `Order.Place` body (`placeOrder`, extracted from `orders/module.ts`) with the resolved session/table and records `channel`, `guestTokenId` / `robotId` on the order; `discountIds` → `DISCOUNT_FORBIDDEN`.
  - `Robot.PairDisplay {deviceId,robotId}` (`device.enroll`, manager/owner): venue record `robot-display/<deviceId>`; the robot screen's identity is the authenticated envelope device id, never a URL or payload robotId.
- Sessions: new `Session.Close {sessionId,expectedVersion?}` for a seating with no live order (empty or all cancelled; prepared bill → `SESSION_FROZEN`, live orders → `SESSION_HAS_ORDERS`), releases the table and bumps `revision`. `Bill.Close` now bumps the revision of the sessions it closes. With W05-T02's move/merge bumps, a token from an earlier seating is dead after move, merge (source and target), close, or bill close.
- Service calls (`service/calls.ts`): `Guest.CallStaff`/`.RequestBill`/`.ReportIssue` (categories food/service/robot/cleanliness/other) create a `service-call` for the guest's own session. Same session+kind(+category): within 30 s of the last request → no-op `{coalesced,cooldown}`; open call after the cooldown → `count+1`; handled call after the cooldown → new call. Retries replay through the operation receipt. `Guest.AcknowledgeCall {callId,expectedVersion}` (staff `order.write`) only marks the call; no bill, payment or session is touched. `Guest.RequestBill` never prepares, settles or closes a bill.
- Missions: `Mission.Guide {destinationId,robotId?}` (table must exist → else `UNKNOWN_DESTINATION`, before any robot is selected) and `Mission.Bus {tableId,unloadAt='wash'}` (collect at a known table, unload at a known station) go through the extracted `createMission` → the existing `selectRobot` path (guide/bussing capability, map binding, battery, safety). `Mission.Cancel` on a **loaded bussing** mission keeps the unload stop pending (no return to the table, no abandonment); cancelling while the robot already waits at the unload point is `UNLOAD_PENDING`; only the unload confirmation ends it (`cancelled`, `loaded:false`).
- Policy: new feature `kiosk.order` (F05); `Guest.PlaceOrder` is gated by the token's signed channel (`qr.order` / `kiosk.order`) or `robot.order` for a paired robot screen, independent of `pos.order` and `robot.delivery`. `guest.call` gates calls/issues, `guest.bill` bill requests, `robot.guide`/`robot.bussing` the missions; `Session.Close`/`Guest.IssueToken` finish existing work (`sessions`). Permissions in `commandPermissions`; roles `kiosk` and `robot-display` (`guest.order`,`guest.call`,`guest.bill`,`catalog.read`) in `rbac.ts`.
- Cloud (`apps/cloud-web/src/server/modules/guest/api.ts`, routes in `routes.ts`, no staff session):
  - `POST /v1/guest/session {token}`: verifies the signature against the active coordinator's enrolled key (`venue_ownership` + `device_enrollment`), expiry, `channel:'qr'` only (`GUEST_CHANNEL_MISMATCH` for kiosk tokens); returns table name, own orders/calls only, and the token's own relay requests with status `pending | accepted | rejected | unknown | unreachable` (pending past its relay expiry = venue never answered → page tells the guest to ask staff).
  - `POST /v1/guest/commands {token,type,payload,operationId}` → `guestCommand` → relay command `actorRef guest:<tokenId>`, device `cloud-guest`, operation id namespaced per token, 2 min expiry, 202 pending. `pendingRelay` gives such commands only `rolePermissions('guest')`; the venue verifies the token again.
  - `GET /v1/guest/menu/:org/:venue` (names, prices, availability, modifiers, image ids; no pricing rules/coupons) and `GET …/images/:assetId` (302 to a 5-min signed URL only for a `menu_image` manifest that is `ready` and named by the current menu; maps/receipts/imports → 404).
  - Pages `(guest)/table/[token]` (`TableSession`: menu, cart, send, call staff, bill request, issue, sent requests with pending/received/unreachable text) and `(guest)/menu/[venueId]?o=<org>` (read-only menu); components `components/guest/{Menu,Cart,TableSession}.tsx`, buttons ≥48 px, VI/EN text.
- Tablet (`apps/tablet-web`): `GuestRequests.ts` (open calls by table, acknowledge; per-seating QR link / kiosk code issue and display), `Kiosk.ts` (holds a staff-issued kiosk token, menu/cart, call staff, bill request; expired seating clears the code), `RobotDisplay.ts` (robot from the device's pairing record; orders/calls only while the robot waits at a table with an open session; safety-stop notice), Fleet screen gains guide/bussing buttons and robot-screen pairing; routes `/guest-requests`, `/kiosk`, `/robot-screen`, nav keys in `packages/ui/locales/{vi,en}.json`. LAN snapshot visibility (`LanService.kt`, mirrored in the dev fixture coordinator): billing roles also see `service-call`, `guest-token`, `robot-display`; guest-facing devices see only configuration, catalog, tables, robots, missions and pairings.
- Lab (plan §4): `lab.guestToken(sessionId,channel?)` issues through `Guest.IssueToken` and encodes the store-signed state; `lab.guestCommand(token,type,payload,operationId?,actor?)` uses the production `guestCommand` builder and the guest principal's authorization. Actors `kiosk` (`device-kiosk`) and `robot-display` (`device-robot`); fixture enables `qr.order`, `kiosk.order`, `robot.order`, `guest.call`, `guest.bill`. Three checkpoint tests now derive their device list from the actor table (the lab enrols every actor device).

## Limits

- Kiosk/robot-screen devices: roles exist and the Android LAN visibility is set, but no physical kiosk or robot screen was run; provisioning those devices needs an owner (a manager lacks `guest.*` to delegate). Guide/bussing are proven with the simulator only; real navigation, guest-following and dish-load safety are W06 robot gates. Voice cues are not implemented (the brief only forbids them being a source of truth).
- QR images are not rendered: staff see the `/table/<token>` path and the kiosk code as text (no QR library in the bundle). Tokens are ~750 characters; a shorter id-plus-signature form can come with printed QR cards.
- The cloud trusts the coordinator key from `venue_ownership`/`device_enrollment`; tokens die when the coordinator epoch changes (handoff), like settlement grants. Guest endpoints have no per-token rate limit yet (each command needs a valid token and becomes one relay row + hint job).
- Local guest HTTPS (guest ordering while WAN is down) is not built: it needs a trusted certificate, local DNS and a static guest bundle served by the coordinator independent of Next.js; the default stays the cloud page, which says when the venue does not answer so staff enter the order.
- Items with modifier groups are shown but not orderable on guest surfaces (staff take those orders); `Payment.Claim` is not exposed on the guest API.
