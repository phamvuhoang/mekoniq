# W06-T03: ROS executor durable journal and native action ownership

Commit: `feat: persist robot execution and recover native action ownership` (`git log --grep 'persist robot execution'`).

Status: **verified_local**. The executor is software-verified against `FakeNativeNavigation`, an in-process (or JSON-file-backed) fake that keeps accepted goals outside the Executor. **No ROS 2, Nav2, Gazebo, onboard Linux computer or physical robot was used.** This is fake-backend evidence, not hardware or Gazebo evidence. The Nav2 bridge (W06-T04) and hardware commissioning (W06-T05/T06) own those gates; this task has no mandatory external gate of its own.

## What was built (`robotics/agent/`)

- `mekoniq_agent/journal.py`: SQLite (`synchronous=FULL`, WAL), mirroring `ExecutorJournal.kt`.
  - `begin()` is ONE `BEGIN IMMEDIATE` transaction: control-epoch fence, no `sending`/`unknown`/open goal, epoch advance, and the `sending` row with the stable goal UUID. It runs before any native call.
  - Statuses are `sending` (journaled, native call outstanding), `accepted` (native ACK), `executing`, `unknown` and `terminal` (outcome succeeded, canceled, aborted or rejected).
  - A row still `sending` on open becomes `unknown/CRASH_BEFORE_RECEIPT`.
  - One executor id per robot (`EXECUTOR_ALREADY_BOUND`). The persisted epoch only rises. Robot-wide STOP intent and per-command cancel intent are persisted until acknowledged.
- `mekoniq_agent/ownership.py`: `Profile` (provisioned scope, map, frame; never taken from a command), plus pure checks for scope (`SCOPE_MISMATCH`, `ROBOT_MISMATCH`), epoch fence, time window and domain.
  - Epoch fence: stale is `STALE_CONTROL_EPOCH`; more than one ahead of the persisted epoch is `CONTROL_EPOCH_OUT_OF_RANGE`.
  - Time window: `EXPIRED_COMMAND` (expiry instant exclusive); `CLOCK_SKEW` if `issuedAt` leads now by more than 30 s or the lifetime exceeds 300 s from now.
  - Domain: `MAP_MISMATCH`, `FRAME_MISMATCH`, `INVALID_TARGET`.
- `mekoniq_agent/executor.py`:
  - `Executor.submit / reconcile / request_stop / cancel / tick / status / state / close`.
  - `NativeNavigation` port: `start(goal_uuid, target, speed_limit_mps)`, `query(goal_uuid)`, `cancel(goal_uuid)`, `request_stop()`. `NativeResult` has `status`, `evidence` and a derived `completed`.
  - The goal UUID is `uuid5(robot/command)`: stable across restarts, persisted before the call, and the key used to query the native side.
  - Order inside `submit`: schema, hash, journal duplicate, STOP unconfirmed, ready, scope, epoch, time, speed, domain, native reconcile, `begin`, native start.
  - A duplicate command id is answered from the journal and never restarted. A changed hash raises `ExecutorError(IDEMPOTENCY_CONFLICT)`.
  - `reconcile()` only queries by UUID and never starts anything. A not-found or unknown goal becomes `unknown` and blocks new goals (`GOAL_UNRECONCILED`). "Never arrived" cannot be told apart from "arrived and forgotten".
  - `ready` is false after a restart with open goals, or while a STOP is pending, until `reconcile()` has asked the native side about every open goal. A new command then gets `NOT_READY`. `Channel.advertise_ready()` refuses until ready.
  - `request_stop` is a request: `{acknowledged, physicalStopConfirmed:false}`. It is journaled first, `tick()` resends it until acknowledged, and `STOP_UNCONFIRMED` blocks the next goal. Open goals become `unknown`. They become terminal only when a native query says so.
  - A speed limit is passed to a backend with `supports_speed_limit`, and refused (`SPEED_UNSUPPORTED`) otherwise. It is never ignored.
  - `completed` means only that the native action reported SUCCEEDED for this goal UUID. It is not localization or arrival proof (W06-T04) and not an exactly-once claim.
  - `fault="before_native_call" | "after_native_accept"` is a test-injected hook. It closes the journal without writing and raises `SimulatedCrash`.
- `mekoniq_agent/protocol.py`:
  - `validate_command` uses the shared `packages/contracts/schemas/wire.schema.json` (`MEKONIQ_CONTRACTS_DIR` overrides, fail-closed if absent). It is never a forked copy.
  - `command_hash` is `sha256(RFC 8785)`, the same bytes as TS `hashPayload` and Kotlin `JournalDatabase.hash`.
  - `parse_strict` rejects duplicate keys and NaN/Infinity.
  - `verify_es256` is **pure-Python** ES256 (P-256, raw r||s, canonical base64url, high-S accepted like the TS verifier). Python had no ES256 verification and the venv has no crypto library, so this avoids a new dependency. It verifies only public inputs and is validated by the shared golden vectors.
  - `Transport` is an outbound-only interface (`send`, `poll`). `Channel` is a signed envelope `{payload, keyId, signature}` with the signature over JCS(payload).
    - Inbound commands from an unknown key, with a bad signature, as duplicate-key JSON or otherwise malformed are dropped before the executor.
    - Outbound results and ready announcements are signed through an injected `signer(bytes) -> signature` hook. No private key is handled in the agent.
- Conformance vectors: `tests/fixtures/contracts/robot-executor-vectors.json` holds the base RobotCommand and its hash, a signed command (an ephemeral key whose private half was discarded), tampered variants, schema-invalid commands, and 10 admission scenarios. They are consumed by **both** `robotics/agent/tests/test_protocol.py` (Python executor) and `tests/contracts/robot-executor-vectors.test.ts` (TS schema/hash/ES256, and the admission scenarios run against the real `ValetudoAdapter` in the protocol emulator). Drift on either side fails a test.

With the journal-duplicate answer, the `begin` open-goal guards and the pre-submit reconcile disabled (a naive "resubmit after recovery" executor), the plan test fails on behaviour: `sqlite3.IntegrityError: UNIQUE constraint failed: executor_command.goal_uuid`, i.e. a second goal with the same stable UUID was attempted. Covered cases (real SQLite files, no mocks of the journal):

- O10: SIGKILL of a real child process after native accept, then recovery in the parent. The same UUID is re-attached with `native.start_count == 1`. Also simulated crashes after native accept and before the native call, and a lost ACK (never resent).
- O11: a partition at submit gives `NO_ACK`; after heal an expired old command is `EXPIRED_COMMAND` and never replayed.
- O20: a handoff (epoch+1) with an unreconciled goal is refused: `NOT_READY` while the native side is unreachable, then `PREVIOUS_GOAL_ACTIVE` once it is reachable, and `GOAL_UNRECONCILED` for an `unknown` goal. The persisted epoch does not advance until the goal is terminal.
- Journal-before-I/O: an independent SQLite connection inside `native.start` sees the committed `sending` row with the goal UUID.
- Duplicate and out-of-order commands: idempotent duplicate, `IDEMPOTENCY_CONFLICT`, stale epoch after a newer one, one goal at a time.
- Forged epochs, scope and domain: forged far-future epoch (it does not fence out later commands, and the persisted epoch survives restart), org/venue/robot mismatch, map/revision/frame mismatch, non-finite target, schema-invalid command.
- Time: stale or expired command, `CLOCK_SKEW` (issuer ahead, lifetime too long), and acceptance within tolerated skew.
- STOP and cancel: not acknowledged, retried by `tick()` across a restart, `STOP_UNCONFIRMED` blocks the next goal, `physicalStopConfirmed` is always false, cancel is scoped to one command. A goal is `completed` only from a native SUCCEEDED; aborted and canceled are not.
- Native rejection is terminal and explicit and does not block the next goal. A speed limit is carried to a capable backend, and refused otherwise.

## Rulings and deviations

- The plan test is adapted by one argument: `Executor(db, native, profile, fault=…)`. Scope and map must be provisioned, and a default scope would fail open. The clock defaults to real time and `command_fixture` to real now, so the snippet otherwise runs as written.
- The plan's `can_submit` snippet is not implemented literally. RobotCommand has no `kind` field (the schema forbids extras), and strict `controlEpoch == owner_epoch` would reject a legitimate handoff. The Kotlin rule is used: not stale and at most one ahead.

## Limits (not claimed)

- No ROS 2 / `rclpy` / Nav2 action client exists here (W06-T04). `FakeNativeNavigation` models goal statuses by name only. Real action semantics (goal expiry, result timeout, preempt) are unverified.
- No MQTT/WebSocket client is bundled. `Transport` is an interface exercised with an in-memory loopback, and the broker, TLS and per-robot ACLs are deployment tasks. The agent never listens, so there is no cloud-direct ROS endpoint. The signed-envelope wire form is local to this channel and is not in `wire.schema.json`.
- The signer hook is tested with a stub. Real key custody (Keystore/HSM/secure element) and trusted-key provisioning are not implemented.
- Pure-Python ES256 is not constant-time. It is for verification of public data only.
- The lease-loss STOP policy (the Android executor's UI lease) is not ported. The ROS agent has no UI lease. A controller-link heartbeat policy belongs with the transport deployment.
- Pytest is not wired into `.github/workflows/ci.yml` (the Python contract test is not either). Run it manually until a Python CI step exists.
- Tested on Python 3.13 only. The pyproject allows >=3.11 (Ubuntu 24.04 ships 3.12, which is not tested).
- The executor refuses a new goal while any goal is `unknown`. Clearing an `unknown` goal needs native evidence or operator action. No operator override exists.
- `trays`/`maxLoadMinor` are admission-time (W06-T01) and are not re-enforced by the executor.
