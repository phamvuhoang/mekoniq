# W07-T01 — Recipes, units of measure and stock consumption

Status: verified_local (software only; SQLite restaurant lab). No device, scale or kitchen hardware is claimed.

## What was built

- `packages/domain/src/inventory/uom.ts`: units (g/kg, ml/l, piece) with dimensions, custom units through per-ingredient `conversions` (`bag: '25000'`), decimal parsing. Conversion is exact or refused: `UOM_CONVERSION_MISSING` (kg→piece with no declared factor), `UNKNOWN_UNIT`, `INEXACT_QUANTITY` (e.g. 0.0005 kg is half a gram). Portions are held in thousandths.
- `movement.ts`: content-addressed ids (`mv-…` from source + recipe version + ingredient + kind) — the realisation of the plan's `stock_movement` unique index, since aggregates are generic snapshots created at version 0 (a racing duplicate fails the store CAS). `issue()` takes stock out at **weighted-average cost**, costing only the covered part: a shortfall is `costKnown:false`, never priced. `receive()` is used by W07-T02.
- `recipe.ts`: `Ingredient.Upsert` (the stock item is ingredient master + running balance; base unit locked once it has movements; `negativePolicy` allow|block) and `Recipe.Publish` (immutable version; base quantities are frozen into the version at publish time; duplicate ingredient / unknown ingredient / unconvertible unit refused; moves the item's `recipe-pointer`).
- `consumption.ts`: `Inventory.Consume {sourceEventId, recipeVersion|itemId, quantity(portions), historical?}` — one `consumption` aggregate per source event. Same source replayed = no-op; same source with another recipe version or quantity = `SOURCE_CONSUMED_DIFFERENTLY`. A historical source whose recipe is gone opens a `stock-exception` and moves nothing (today's recipe is never substituted); a live one is `RECIPE_NOT_FOUND`. `Inventory.RecordWaste`: raw spoilage deducts stock; `consumedSourceEventId` form reclassifies an already-prepared dish as waste (bounded by what was consumed, `WASTE_EXCEEDS_CONSUMED`) and **never restocks**.
- Wiring: permissions `inventory.write` (manager) / `inventory.consume` (chef, manager); feature `inventory` — `Ingredient.Upsert`/`Recipe.Publish` are new work (blocked while draining), consume/waste are `finish_existing`. Kitchen tickets now carry `itemId`; the tablet Kitchen screen issues `Inventory.Consume` after an accepted `Kitchen.Ready` (source id = ticket + cumulative prepared count, items without a recipe are skipped). Screens `Inventory.ts` (balances, negative warning, waste form, add ingredient) and `Recipes.ts` (versions, current marker, publish form); `/inventory` in the main nav, `/recipes` under Manage. `LanService.kt` lets the kitchen role read `stock-item`, `recipe`, `recipe-pointer`.
- Fixtures: `restaurant-v1.json` enables `inventory`, adds `rice-raw` (10 000 g worth 200 000) and `rice-v1` (200 g per portion); the lab seeds them plus the `rice` recipe pointer.

## Limits

- The recipe used for a Kitchen.Ready deduction is the **current** one when the tap happens (pinned into the consumption record), not the one current when the order was placed; per-order recipe pinning would need a snapshot on the order line. A recipe published between order and ready therefore applies to that portion.
- Weighted-average only; FIFO/cost layers are not implemented (plan: first version weighted-average).
- `Ingredient.Upsert` conversions apply to future recipes/receipts only (recipes freeze their base quantities).
- Android: `LanService.kt` visibility edited; Kotlin not compiled/run here. Tablet screens are type-checked only (no browser spec for inventory).
