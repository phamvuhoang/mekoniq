#### Important

1. **A contradictory terminal report can archive a completed run and destroy its recovery proof.** src/ui/control-panel.ts:147–152 checks the confirmed tick but accepts a report for the same run and tick that changes a confirmed completed outcome to cancelled and supplies null tuning. It immediately archives. The null-result branch also skips the echoed bench request, signal and control profile identity. Source packages/lab-runtime/src/v2/control/bench-runner.ts:525–542 emits the request and outcome. Validate those fields before either archive path and bind report status to the last confirmed terminal evidence. An explicit proof reclaim can legitimately change the current status to needs_attention while preserving the original tuning (Source bench-runner.ts:390–401,509–514). Account for the verified reclaim receipt and preserve reread when expected result evidence is unavailable. tests/unit/control-workbench.test.ts:533–537 only changes the tick.

2. **Known but impossible action statuses trigger automatic archive after an uncertain mutation.** src/ui/control-panel.ts:219–230 admits START→ready and STEP→ready with an increased revision and unchanged tick. Lines 240–245 skip report reading for ready, then lines 257–259 automatically archive. A corrupt response can therefore close a worker whose actual START or STEP outcome is unknown. Validate the action-specific statuses, start/cancel ticks and the maximum step advance, including legitimate terminal-at-start and zero-progress terminal cases. Route impossible receipts to explicit recovery with no automatic mutation. tests/unit/control-workbench.test.ts:572–575 exercises an unrecognized status only. Source bench-runner.ts:410–438 has the actual transitions.

3. **A missing CREATE proof can still start a worker.** src/scenarios/controls.ts:217–223 returns the CREATE view when reclaimToken is absent, empty or otherwise unusable. src/ui/control-panel.ts:234–241 accepts the run and sends START. After a disconnect or re-pair the browser can have no usable credential for that known run. The Source gateway issues the proof in every successful CREATE receipt (packages/lab-runtime/src/v2/gateway.ts:303–306). Check the proof before starting a bench. Keep an identified run attributable to its original target and describe recovery limits for a malformed receipt. Exercise a 201 with a valid view and missing or empty proof.

4. **Disconnecting during START or STEP loses reread for a known run.** src/ui/control-panel.ts:239–245 keeps the confirmed bench and its request context in a local variable until a terminal action. Pending START or final STEP followed by disconnect/re-pair takes the inactive path at lines 248,257. Invalidation makes its mark stale at lines 78–82. On return to the issuing target the run has an orphan Close action at lines 329–332, but no entry for Read again. A worker can have completed the final STEP before its response reaches this tab. Preserve the bench in issuing-target history immediately after confirmed CREATE, keep in-flight controls unambiguous, and offer explicit reread after reconnect. tests/unit/control-workbench.test.ts:479–485 starts disconnection before CREATE supplies an ID, so it misses this case.

5. **Malformed health can bind the selected joint to another joint's gain fields.** src/control/workbench.ts:129–137 accepts an MJ-BENCH-ARM entry with axis J3 and axisIds containing xarm-1/J4 if the latter appears in the profile and envelope. Distinct catalog rows can likewise identify the same drive axis. src/ui/control-panel.ts:195–196,214–216 then edits J4's gains and requests a J3 bench. The frozen Source derives the actual joint from the selected axis (packages/lab-runtime/src/v2/control/bench-runner.ts:63–72). Later result validation is too late to prevent the wrong bench from running. Validate the axis-to-drive ID correspondence, cross-row uniqueness and ordered wheel identity before enabling Run bench. tests/unit/control-workbench.test.ts:492–495 covers an invalid loop and reversed numeric bounds.

#### Expected receipts and recovery cases for the fix

| Operation | Accept from the pinned Source | Treat as uncertain or unreadable |
| --- | --- | --- |
| CREATE | Ready at tick 0, expected run identity, nonempty issuing-runtime proof. | Missing identity or proof, nonzero initial tick, or non-ready success. Send no START. Without an ID, CREATE owns no engine and the session/open-run policy applies. With a known ID but unusable proof, retain the ID on the issuing target and expose only recovery the current credentials permit. |
| START from ready | Running at tick 0, or completed at tick 0 for an initial collision, fault or unstable engine. | Ready, paused, cancelled, or a tick advance. A failed start may produce a non-2xx error and needs-attention state on the server. Do not interpret a contradictory 2xx as successful cleanup. |
| STEP from running | Running after the requested batch advances in full, or completed/needs_attention within the requested span. Terminal reads can stay at the prior tick after instability or worker loss. | Ready, paused, cancelled, regression, overshoot, or running after zero/partial progression. Keep confirmed request, ID and proof without sending another mutation. |
| CANCEL from running or paused | Cancelled at the prior tick. | Changed tick or any other successful status. Preserve explicit recovery and do not repeat cancel. |
| Read/report after confirmed terminal | Same run, historical identity, tick and compatible confirmed outcome, including matching echoed bench request with the profile reference. A confirmed proof-based reclaim returns a reconcile-only needs_attention view. An original completed result may still be present. | Completed→cancelled/null, missing expected completed tuning, or inconsistent report identity. Preserve known tuning/trace and the reread action. A genuine stopped run with validated null tuning can close. |

- Keep receipt revisions monotonic for all actions. An idle expiry during a STEP can itself advance the revision, so a blanket revision delta of exactly one would reject a legitimate terminal receipt. Source control/bench-runner.ts:354–355,370–373,400–438,447–455,461–476.
- Exercise known-ID disconnect, retarget away and back, explicit re-pair and an expiry/401 during START or final STEP. Late results must leave the active target untouched. Returning to the issuing target should offer Read again and Close after confirmed proof-bearing CREATE. Re-read may first return ownership 404, requiring explicit proof reclaim and a new read. A read, trace, archive, or archive-acknowledgement failure must retain the proof and known result. Closing after successful archive can remove proof while preserving the recorded result, export and A/B. A receipt arriving after an unknown CREATE timeout may attach only to its issuing target. A missing identity/proof may constrain recovery and must be represented truthfully. See src/ui/control-panel.ts:78–106,120–166,234–259,263–270,329–332.
