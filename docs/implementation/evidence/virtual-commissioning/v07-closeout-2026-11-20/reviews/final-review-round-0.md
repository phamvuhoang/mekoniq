### Important

1. **The private backup contains the original run signing keys.** The backup restriction is in `source/docs/superpowers/plans/2026-11-20-r4-v07-closeout.md:131`. `source/packages/lab-runtime/src/v2/session.ts:35` persists the private signing JWK under `signing-key.json`. I checked property names without displaying any key material. The restored current CIL archive contains 44 private EC keys and the restored historical archives contain 58. Access to the draft would allow its reader to sign simulation journal entries under those recorded run identities. Access controls narrow exposure. They do not turn private signing keys into shareable evidence.

   Retain immutable local originals. Publish separately identified verification copies containing the public JWK fields `kty`, `crv`, `x`, `y`, which are exactly what `source/packages/lab-runtime/src/v2/control/campaign-source-evidence.ts:19` uses. Preserve the recorded journal bytes and signatures. Account for changed key-file bytes in each dependent `case.json` inventory, top-level checksum list, transport member index and archive checksum. Record before/after hashes and the limited representation change, audit *all* packaged members for other signing material/runtime credentials, and verify the reconstructed copies using the standard offline readers. Replace the affected draft assets, stale backup hashes and recovery instructions. Document that the original keys were available to draft readers and that a checksum of an original is distinct from the downloadable sanitized bytes.

2. **A duplicate recording can satisfy the DRV06 repeat check.** `source/packages/lab-runtime/src/v2/control/cil-campaign.ts:167` matches run identities within each case. At lines 210–216, `verified` retains the stream digest and deficits, but no run UUID. Feeding the same execution under two registered case labels therefore satisfies the per-case source checks and the bit-identical oracle. This can produce a false pass for the contract requiring independent executions. The actual fresh archive contains **44 distinct UUIDs for 44 records** across 38 cases and six nested legacy comparisons. This establishes that the current recording has separate identities. Require unique run identities across the cases participating in verification, including baseline/repeat pairs and the nested ideal/legacy comparison, before crediting equivalence. Add a duplicated-execution regression and re-verify the authentic archive.

3. **The trace shown in the Lab is not bound to the result it displays.** At `source/packages/lab-runtime/src/v2/control/bench-runner.ts:397`, the endpoint drops `manifestSha256` and run identity already available from the reader. `lab/src/control/workbench.ts:147` checks axis order, timing, sample types and counts. `lab/src/ui/control-panel.ts:202` then accepts the data and archives the run. Two complete trials of the same axis typically have the same 500-tick shape even when their gains and signals differ. A valid stale trace response for the other trial can therefore be shown alongside the current trial’s metrics, followed by archive. Return the run ID and verified trace manifest digest on the trace receipt and compare them to the accepted `TuningResultV1.runId` and `.trace.sha256` before plotting and archiving. Cover swapped valid traces of the same axis and length, and recovery once the correct trace is received. Existing readers already calculate the digest, so this does not require a change to the physics or saved trace format.

4. **The offline bench verifier can certify a malformed result or contradictory outcome.** `source/packages/lab-runtime/src/v2/control/bench-campaign.ts:73` casts the JSON and tests that `tuning` is truthy. The acceptance field required to equal false by `source/packages/contracts/schemas/control-evidence-v1.schema.json:443` is never consulted. At `bench-campaign.ts:92`, the code checks a tuning status and tick, leaving the outer `report.outcome.status` unchecked. A cancelled report paired with a completed tuning result at tick 500, or an embedded result marked accepted, would clear this verifier after inventory refresh. At `bench-campaign.ts:86`, omitting both wheel metadata and the recorded final body observation also bypasses the new check even for `bench-v2`. Use the existing production tuning schema validator before consuming the object. Check the outer finished-run status against the recording contract and require the v2 wheel fields/comparison explicitly for the registered successful wheel cases, retaining genuine historical v1 compatibility. All 16 current reports inspected have machine acceptance false and both outcomes completed. Both wheel comparisons name tick 500.
