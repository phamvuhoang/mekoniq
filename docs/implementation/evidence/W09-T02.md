# W09-T02 — Chain reports and shared entitlements

Status: verified_local (local PostgreSQL 17 + the real cloud modules + the real domain registry in the restaurant lab). No hosted Supabase, no tablet, no second coordinator.

## What was built

- `chain/reports.ts` `chainReport` (`GET /v1/chain/reports?kind=chain-sales&businessDate=&venues=&format=csv`): for every branch the actor holds `report.read` for, the same per-branch `sales` report the branch sees (`readReport`: applied facts only, watermark, venue time zone). Output per branch: status, reason, `appliedAt`, `lagMs`, `pending` backlog, time zone (+ whether assumed), currency, totals, unreconciled difference. Consolidation: `totalsByCurrency` (currencies are never added together), `includedVenueIds`, `incompleteVenueIds` (not `current`, or no known currency), `complete`. A branch with no applied data has `totals:null` and is left out of the totals — never a zero. `businessDateBasis: venue-local` (each branch's own business day), `consolidatedTimeZone: UTC` (only the stamp of `asOf`). CSV prints a `# complete=… incomplete=…` header and per-row freshness.
- Scope: an actor sees only branches it holds `report.read` for; naming another branch is `SCOPE_DENIED`. No venue-scoped table is read without `withTenant` for that venue.
- `chain/shared-entitlements.ts` + migration `20261104000200_chain_shared_balance.sql`: a cloud-owned pool (`chain_shared_balance`), cumulative per-branch grants (`chain_shared_grant`) and per-operation idempotency (`chain_shared_operation`). `reserveSharedBalance` takes exactly `count` out of the pool once per `operationId` (retry → `duplicate:true`, same grant; same id with different content → `IDEMPOTENCY_CONFLICT`; not enough → `SHARED_BALANCE_EXHAUSTED`), then relays `Voucher.ReceiveEscrow` (cumulative total + revision, so a lost or repeated relay cannot double-credit the branch). `reconcileSharedBalance` reads what the branch has applied (its voucher escrow slot): issued / confirmed / unconfirmed / used / returned / outstanding (`remainingEscrow`), credits the pool from the branch's own cumulative `returned` (idempotent), and with `release` asks the branch to give back its unspent remainder (`Voucher.ReturnEscrow`, one unanswered request at a time).
- Domain (venue side, `promotions/voucher.ts`): `Voucher.ReceiveEscrow` (creates the shared voucher mirror with `remaining:0` if absent; cumulative `total` + `revision`; older revision = no-op; a total that goes backwards is refused) and `Voucher.ReturnEscrow` (only unspent uses, `returnRevision` idempotent). Permission `promotion.write`, feature `promotion`; relayed through `relayVenueCommand(…, {internal:true})`, not added to the admin allowlist.
- Routes `/v1/chain/reports`, `/v1/chain/shared-balances[/:id[/reserve|/reconcile]]`; page `/admin/chain/reports` (`ChainReports.tsx`).

## Limits

- "Duplicate branch journals" are de-duplicated by the existing sync ingest (unique entry/aggregate in `sync_projection`); this task does not re-test that path.
- The branch-to-cloud return/credit path depends on the branch syncing its voucher fact; until it does, the units stay reserved (by design: never credited on timeout). There is no scheduled reconcile job.
- Online redemption against the pool (no allocation) still does not exist; shared vouchers are spent only from an allocation. Loyalty points sharing across the chain is not part of this task (W08-T02 ledger stays per venue).
- Reports are recomputed per request for each branch (the existing `readReport` ponytail ceiling applies per branch). UI type-checked/linted only.
