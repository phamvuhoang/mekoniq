## What was built

- `packages/domain/src/configuration/trial-import.ts`: two commands on the production registry (`createProductionRegistry`) and on the restaurant lab, permission `configuration.publish` (manager and owner, not cashier).
  - `Trial.ImportPreview {input}`: dry-run. No events, no effects. Returns the report (`status`, `previewHash`, `schema`, `rejectedFields`, `unmappedFields`, `blocking`, `legacyFeatures`, `featurePlan`, `points`, `robots`, `menu`, `timing`). The key is `liveEffects:'none'` (a decision value named `effects` is the outbox).
  - `Trial.ImportApply {input,previewHash}`: recomputes the report, refuses on any blocking item, a `previewHash` mismatch (`PREVIEW_CHANGED`), then writes: `station`/`table` aggregates for new points (existing ones kept), one non-dispatchable `robot` per trial robot, and one `trial-import` record (`TrialConfigurationImported`: menu draft, timing, feature plan, unmapped fields).
  - Whitelist `name/points/robots/menu/timing/features`. Known static trial settings (`rev`, `trays`, `dishPoint`, `roles`, `featurePolicyVersion`, `serviceProfile`, `customerCancel`, `service`, `notes`, `payment`, `floor`, `map`, `sim`) are reported as unmapped. Any other top-level key is rejected: runtime names (`missions`, `orders`, `bills`, `sessions`, ...) as `RUNTIME_STATE`, the rest as `UNKNOWN_FIELD`. A rejected input is refused as a whole, so it has zero effects.
  - Blocking codes: `RUNTIME_STATE_REJECTED`, `UNKNOWN_FIELD_REJECTED`, `UNSUPPORTED_SCHEMA_VERSION` (anything but absent/1/2), `INVALID_*`, `UNKNOWN_DRIVER`, `STALE_POINT_REFERENCE` (robot dock, `valetudo.points` key, menu category station), `STALE_CATEGORY_REFERENCE`, `POINT_KIND_CONFLICT`, `ROBOT_EXISTS`, `TRIAL_IMPORT_ALREADY_APPLIED` (same plan imported twice is refused, not doubled).
  - Imported robots: driver `valetudo` or `simulator` (trial `sim`/absent) only; `validation` is `integration_tested` (a simulator stays `simulated`); `capabilities:[]`, no map, no bindings, `trays:0`, `battery:null`. They fail admission with `VALIDATION_INSUFFICIENT` / `TARGET_UNBOUND` / `CAPABILITY_UNSUPPORTED`; `Robot.BindMap` is refused (`MAP_NOT_REPORTED`) until the robot itself reports a map. Teaching points (`valetudo.points`, topic) and x/y are never bound.
  - Menu: an unpublished draft inside the import record (integer price -> minor-unit string; a non-integer price is `INVALID_PRICE`). The catalog is untouched.
  - The active configuration is never changed: the legacy features become a plan (`featurePlan.enabled`) to apply with `Configuration.Apply`.
- `packages/domain/src/policy/presets.ts`: `trialFlagFeatures` is exported and gains `busRobot -> robot.bussing`; an explicit `false` now switches the feature off (needed so `busRobot=false` disables the bussing in the base profile); **`pay` now maps to `payment.transfer.manual`** (the trial's staff-verified transfer) instead of the bank-integrated `payment.transfer`, which can never be ready. This is a behaviour change to an earlier decision (W02); the cloud feature settings screen and `feature-policy.test.ts` still pass.
- `scripts/import-trial-config.mjs`: dry-run only. One user-exported file path, no network, never reads `../trial`, writes nothing. Exit 0 ready, 2 rejected, 1 usage/IO. It evaluates no venue state (`venueChecks: not_evaluated_offline`).
- Tablet web UI (genuine gap found by the preset spec, implemented generically): `apps/tablet-web/src/router.ts` `screenFeatures` / `featureOn`. A screen is offered in the navigation, and opens, only while one of its features is `enabled` or `draining` in the applied configuration; otherwise the panel "Chức năng đang tắt". Display only (the coordinator guard enforces); no configuration snapshot hides nothing; reports stay.
- Test support (dev lab only): `tests/support/lab.ts` carries the applied configuration revision as `policyRevision` after an accepted `Configuration.Apply`, and `/session` of the fixture coordinator reports it (before, every command after a revision change was `POLICY_STALE`; a refreshed tablet carries the new revision). `tests/support/restaurant-lab.ts` `importTrial(input)`: preview, then apply with the preview hash, through `lab.command`. The restaurant lab registers `registerTrialImport`.
- Fixtures: `tests/fixtures/trial/site-baseline.json` (copy of `../trial/data/site.json`), `site-demo.json` (copy of `site.demo.json`, all flags on). Nothing under `../trial` or `../web` was written, no trial script or `deploy.sh` ran, ports 1880/1884 and robot addresses untouched.

## Limits and external blockers (`blocked_external`)

- **Gate B is BLOCKED.** No approved robot model/firmware, signed commissioning or venue acceptance; no physical hardware; no real-device O01/O10/O11 on a supported Android pair and venue LAN; no real robot map to bind. The pilot spec's real-device test is skipped with a `PREREQUISITE:` reason and throws even when `MEKONIQ_PILOT_DEVICE` is set, because no automated physical harness exists.
- The preset spec runs on the dev lab's restaurant fixture venue. Cloud enrollment of an empty venue and tablet pairing cannot be driven there; the real configuration commands are used instead. It does not drive a robot trip (imported robots are not dispatchable).
- The import writes the feature plan but does not switch features; a manager applies it with `Configuration.Apply`. There is no tablet or cloud screen for the import yet (command and script only).
- Shadow-mode telemetry ingestion is documented in the dossier only; implementation and the actual cutover are W11 after the deploy result is reviewed.
- Parity gaps (customer-cancel policy, request station, timing enforcement, KPI, bank-instruction display, close-while-delivering, retarget) are listed in `trial-service-parity.md`. Simulation says nothing about payload, braking or safety.
- `.github/workflows/ci.yml` untouched. The wave acceptance boxes in `2026-10-30-wave-06-real-robots.md` are left unticked: per-model hardware evidence and Gate B are absent.
