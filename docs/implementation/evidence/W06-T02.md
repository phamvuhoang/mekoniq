# W06-T02: Valetudo REST/MQTT transport and completion evidence

Commit: `feat: integrate valetudo through evidence-based navigation adapters` (SHA recorded in the follow-up docs commit).

Status: **blocked_external**. The software is done and verified locally against a protocol emulator, and on the dedicated AVD `mekoniq-wave01-test`. **No physical Valetudo robot, robot firmware, venue LAN or broker was used.** Nothing here is hardware validation. The `valetudo` profile stays at `integration_tested` at most, and `profileReason` keeps it undispatchable. Remaining: the supervised hardware proof in `docs/operations/valetudo-profile.md`.

## What was built

- **Pinned API.** Valetudo 2026.10.0 (<https://github.com/Hypfer/Valetudo/tree/2026.10.0>; the files read are listed in `tests/fixtures/valetudo/pin.json`). Fixtures in `tests/fixtures/valetudo/` (robot, capabilities, state attributes, ValetudoMap v2) are shapes transcribed from those sources, not robot recordings. Routes and the MQTT layout are in `docs/operations/valetudo-profile.md`.
- `packages/robot-adapters/src/valetudo/`:
  - `capabilities.ts`: pinned routes; required capabilities (GoTo + BasicControl); `ValetudoProfile` with tolerance knobs; `lanEndpoint` (only a private-LAN or `.local` http(s) origin, no credentials, path or query; loopback only with an explicit test option); `validateProfile` (transport, MQTT topic ids, positive knobs).
  - `map.ts`: `parseMap` (ValetudoMap v2, cm, `robot_position`/`go_to_target`, fingerprint `sha256(JCS{size,pixelSize,segments})` as a map-change detector, not an identity), `parseStatus`, and `sampleOf` (incl. host uptime).
  - `completion.ts`:
    - `arrivalConfirmed` (the plan snippet, verbatim).
    - `assess`: completed only after a non-retained `moving` sample with a matching `go_to_target`, then a fresh stationary idle stretch within tolerance on the same map, with no gap, reboot (uptime decrease), other status or other target. Without that the goal is pending, and at the trip deadline it becomes `unknown` with a reason.
  - `reconcile.ts`: `executionState`. A command with no journal row is `unknown/NO_GOAL_QUERY`; Valetudo has no goal query.
  - `adapter.ts`: `ValetudoAdapter implements RobotAdapter`.
    - Before any I/O it refuses: robot mismatch, stale control epoch, expired command, speed limit (`SPEED_UNSUPPORTED`), map/frame mismatch, an active previous goal, an unconfirmed stop, missing capabilities, an unreachable or retained-only robot, and a changed map.
    - The goal is recorded as `sending` before the goto. The same command ID is answered from that record, and a changed payload is `IDEMPOTENCY_CONFLICT`. It is never resent.
    - It emits accepted, progress, completed, cancelled, failed, unknown and `safety_state` at most once each.
    - Cancel and requestStop only acknowledge the request. The next goal waits for stationary evidence.
    - The transport is fixed at construction (`TRANSPORT_MISMATCH`), so it never switches mid-trip. `executor:'native'` is set only for the native transport.
  - `rest.ts`: REST v2 transport. No redirects, a timeout, and body caps after gzip inflation (`MAP_TOO_LARGE`). 200 maps to accepted, 400 to rejected, anything else or no answer to unknown.
  - `mqtt.ts`: Homie transport over a minimal `MqttConnection`. Commands are QoS 1 with `retain:false`, and only under the robot's own base topic. Retained deliveries are marked and never used as evidence. Map-data is inflated with `maxOutputLength`. A `$state` that leaves `ready` latches a gap. A broker PUBACK is not acceptance: `accepted` needs motion evidence. **No MQTT client library is installed**, so production client wiring with per-robot ACL credentials is a deployment task. Tests use an in-process fake broker.
- `dispatch.ts` / `contract.ts`: `RobotAdapter.executor?:'native'`. `dispatchRobotEffects` still refuses every non-simulated adapter unless `executor==='native'` (`NATIVE_EXECUTOR_REQUIRED`).
- Domain (carried W06-T01 ruling):
  - `Robot.Observe` handles `safety_state` at robot level, with or without a mission. It checks the control epoch and accepts `clear`, `fault` or `estop`, recorded as `RobotSafetyObserved`.
  - `nextStop` holds the next leg as `needs_attention/SAFETY_NOT_CLEAR` with no command issued, so confirmed cargo still commits.
  - `Mission.Resume` refuses `SAFETY_NOT_CLEAR` until a `clear` observation arrives. Admission already refused it.
- Android native executor, `apps/tablet-android/android/app/src/main/java/io/mekoniq/tablet/executor/`:
  - `ExecutorJournal.kt`: its own SQLite DB with `synchronous=FULL`.
    - One executor binding per robot (`EXECUTOR_ALREADY_BOUND`), and a persisted control epoch (`STALE_CONTROL_EPOCH`).
    - The `sending` row is committed before I/O; the receipt and observations after.
    - On open, a `sending` row becomes `unknown/CRASH_BEFORE_RECEIPT`.
  - `NativeRobotTransport.kt`: the only tablet code that sends robot mutations. It uses the REST v2 routes above with the same LAN-origin rule, no redirects, bounded bodies and the same map fingerprint as TS.
  - `ExecutorService.kt`:
    - `ExecutorProfile` comes from the managed restriction `valetudoProfile`.
    - `ValetudoExecutor` handles submit, reconcile, cancel, requestStop, observations and tick. The UI lease is renewed by any bridge call. When the lease is lost mid-trip with the `stop` policy, it journals the stop and sends one STOP. It never reports `completed`.
    - Before superseding an earlier goal it needs a fresh idle sample with no `go_to_target`.
    - The foreground `ExecutorService` keeps polling and journaling while the UI is suspended.
  - `ExecutorPlugin.kt`: Capacitor `Executor` (submit, reconcile, cancel, requestStop, observations). Only commands, command IDs and reasons cross it, never URLs. Registered in `MainActivity`, with the service declared in the manifest.
  - `src/debug/res/xml/network_security_config_debug.xml`: debug-only cleartext to `10.0.2.2`.
- `apps/tablet-android/src/robot-executor-bridge.ts`:
  - The typed `Executor` plugin and `NativeExecutorTransport`. `restore` rebuilds a goal from the native journal after a WebView reload, so the shared rule judges it.
  - `startNativeValetudoRuntime`: dispatches effects through the native adapter, runs telemetry rounds and forwards events as `Robot.Observe`. It authorizes only a dispatchable profile, which never holds on emulator evidence.
- Test rig `tests/support/valetudo-rig.ts`:
  - The protocol emulator (REST + Homie MQTT via a fake broker) supports `acceptGoto`/`rejectGoto`/`failGoto`/`silentGoto` (delayed, no ACK, 5xx), `telemetry`, `driving`, `idleAt`, `reboot`, `unreachable`, capability override and map padding.
  - `createValetudoRig()` provides the real adapter, a fake clock, `command(id)`, the `events` collector, `tick` and `close`.
  - A CLI entry serves the AVD test. The `/__lab/*` control routes exist only in this test emulator.
- `scripts/test-runner.mjs`: the `adapters` suite is registered.

The conformance cases are:
- the plan snippet;
- HTTP 200 with idle at the goal and no motion (pending, then `unknown/NO_MOTION_EVIDENCE`);
- full evidence giving exactly one `completed`, with 25 m/12 m sent as 2500/1200 cm;
- idle away from the goal, and no pose;
- stale telemetry (gap);
- a reboot faster than one poll (uptime gives `REBOOTED`) and a seen reboot (docked);
- a map change and a foreign `go_to_target`;
- no ACK when the reply is late, never sent or a 5xx (unknown, a single goto, never resent);
- same-goal resend and duplicate delivery (one goto), and `IDEMPOTENCY_CONFLICT`;
- speed limit, expiry, map, frame, robot and capability refused with no I/O, and a stale control epoch;
- STOP/cancel then retarget waiting for stationary evidence, not time;
- error giving failed plus `safety_state` fault/clear;
- gzip and deflate maps over the cap;
- endpoint and profile validation;
- the manifest below hardware level, `NATIVE_EXECUTOR_REQUIRED` and `TRANSPORT_MISMATCH`;
- MQTT: retained-only telemetry refused, commands never retained, acceptance only on motion, broker down, the per-robot ACL, and `$state` lost;
- the native bridge fake: commands only, the shared rule over native-journaled samples, restore after a WebView reload, and `NO_GOAL_QUERY`.

The AVD cases are:
- a crash between journal and receipt gives `unknown/CRASH_BEFORE_RECEIPT`, and the same command is never sent (0 gotos);
- after a reopen, the same command is answered from the journal (1 goto);
- a stale control epoch is refused across a reopen with no I/O;
- with the UI suspended, the journaled arrival evidence is never self-acknowledged as `completed`;
- a lease loss sends one STOP and the goal becomes `unknown/LEASE_LOST_STOPPED`; the retarget is refused while the robot is still moving and accepted once it is idle;
- a speed limit, foreign endpoints, a second executor ID and an MQTT profile are refused;
- the Kotlin map fingerprint equals the TS fingerprint.

## Limits and external blockers

- Protocol emulator and AVD only. These results are `integration_tested` evidence and say nothing about real firmware timing, `go_to_target` support, pose noise, safety or payload. **Supervised hardware proof is blocked_external**: a physical Valetudo robot, the named model and firmware, the venue LAN and a supervisor are all required. See `docs/operations/valetudo-profile.md`.
- MQTT is protocol-tested only against an in-process fake broker. No MQTT client library is installed, and the native executor is REST-only (`TRANSPORT_UNSUPPORTED` for MQTT).
- Release builds have cleartext disabled. Reaching a plain-HTTP Valetudo from a release tablet needs a venue decision (a release network-security config for the provisioned host, or TLS in front of Valetudo).
- Arrival needs firmware that exposes `go_to_target` during a GoTo. A robot already at the goal never "arrives", because a goto produces no motion evidence, and the goal ends `unknown` at the deadline. This is deliberately conservative.
- The tolerances (0.40 m / 5 cm / 5 cm / 2 s / 3 s / 120 s) are rig values to be measured per robot, not hardware facts.
