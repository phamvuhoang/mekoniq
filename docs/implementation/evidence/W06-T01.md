# W06-T01: Capability registry, map binding and traffic admission

Commit: `7fc5fb4 feat: admit missions only to validated robot capabilities`.

Status: verified_local. Software only: SQLite restaurant lab, local Supabase PG17 for the cloud-backed regression files, deterministic simulator. **No physical robot, Valetudo/Nav2 endpoint or vendor firmware was used. No hardware validation, VDA 5050 compatibility, payload safety or Gate B result is claimed.** The `hardware_validated` robots in the tests are seeded profiles that exercise the admission rule; they prove nothing about any hardware.

## What was built

- `packages/domain/src/fleet/capabilities.ts`: driver capability registry (`simulator`, `ros2`, `valetudo`): target kind, native length unit (`m`/`cm`), the capabilities a driver can carry at most, speed control, zone enforcement, docking. A robot's own manifest state must also claim the capability, speed control (`speedControl:true`) or zone enforcement (`zoneEnforcement:true`); the driver entry only caps it.
  - `profileReason(robot)` is the single R-W06-VALIDATION predicate: a simulator only as `simulated`, any other driver only as `hardware_validated`/`venue_approved`; `integration_tested` is never dispatchable; a driver missing from the registry is `UNKNOWN_DRIVER`. `policy/readiness.ts` `runtimeReadiness().robot` now uses this same predicate (no second copy).
- `fleet/map-binding.ts`: `bindingCurrent` (plan snippet) and `bindingReason(robot,targetId)`. A target is current only if the robot's operator binding epoch `bindingRevision` equals the map revision the robot reports now (`mapRevision`) and the taught waypoint carries that `mapId/mapRevision`. A same-size map proves nothing. A map reset (new reported revision) makes every binding stale (`MAP_BINDING_STALE`) until it is rebound.
  - `Robot.BindMap {robotId,mapId,mapRevision,frame,units,waypoints,parkingPoint?,chargingDock?}` (manager, `robot.configure`). It binds only the map the robot reports right now (`MAP_NOT_REPORTED`). Frame and units are required (`FRAME_REQUIRED`, `UNITS_REQUIRED`). x/y are converted to domain metres (`cm`/`mm`/`m`) and yaw is radians within ±π (`INVALID_POSE`). Points must be venue tables/stations or the robot's home points (`UNKNOWN_POINT`). Bindings merge; ones still on an older revision stay stale and are listed in `value.stale`.
  - `homeTarget(robot)`: the charging dock when it is taught on the current map, otherwise `parkingPoint`. `Mission.Create {robotId,target:'home'}` uses it and needs a robot (`ROBOT_REQUIRED`).
- `fleet/admission.ts`: `eligibleRobots(mission,profiles):Eligibility[]` gives each robot `{robotId,eligible,reasons[]}`. It checks profile, capability, a current binding for **every** stop, trays, payload (`loadMinor` grams vs `maxLoadMinor`, BigInt), speed control when `speedLimitMps` is requested, and footprint `widthM` vs a venue point's `clearanceM` (an unknown footprint never fits a constrained point). Then it checks safety, battery and availability. All of this runs before scoring.
- `fleet/scheduler.ts`: `selectRobot(robots,demand,requested)` is now a thin scorer over eligible robots (idle first, battery, id). An explicit `robotId` is not a bypass: it is rejected with that robot's first reason (e.g. `MAP_BINDING_STALE`, `CAPABILITY_UNSUPPORTED`, `OVERLOADED`, `SPEED_UNSUPPORTED`, `FOOTPRINT_TOO_LARGE`, `UNKNOWN_DRIVER`, `VALIDATION_INSUFFICIENT`). `any` with nobody eligible stays `NO_CAPABLE_ROBOT`. `missionDemand` builds the demand from a payload or a queued mission's state.
  - All callers go through it: `Mission.Create` (now also takes `target` as a one-stop shorthand, plus `loadMinor`/`speedLimitMps`, kept on queued missions), queued assignment in `nextStop`, `Mission.Guide`/`Mission.Bus`. `retarget.ts` (W05-T02 session move) now requires a *current* binding for the new table, not just a present one.
- `fleet/reservations.ts`: `Zone.Reserve {zoneId,robotId,missionId?,ttlMs?}` / `Zone.Release {reservationId,evidence?}` (executor `robot.traffic`; a manager may release). Aggregate kind `reservation`, id `<zone>@<robot>`, which robot reconciliation and the recovery inventory already treat as held until released.
  - A zone is shared only between robots of the same driver that both enforce zones. A robot that does not enforce zones is serialized (`pending`, `ZONE_SERIALIZED`). A different vendor never shares (`pending`, `MIXED_VENDOR_TRAFFIC`). Pending reservations wait with their reason, and a release promotes them in request order.
  - A holder whose robot is unknown (stop requested / lost) becomes `unknown` and keeps the zone (`ZONE_HELD_UNKNOWN`). **TTL never releases it.** Releasing it needs written evidence (`EVIDENCE_REQUIRED`). Only an expired holder whose robot is known idle lapses (`releaseReason:'ttl_lapsed'`). A holder asking again only renews its TTL and is never downgraded.
- Wiring: handlers registered in `restaurant.ts`, with permissions `Robot.BindMap:robot.configure` and `Zone.Reserve`/`Zone.Release:robot.traffic`. Features: `Robot.BindMap` and `Zone.Release` map to `fleet` finish_existing, so they still work while the fleet drains. `Zone.Reserve` is `fleet` new unless it serves an open mission. RBAC: manager +`robot.configure`,`robot.traffic`; executor +`robot.traffic`. `Venue.Configure` simulated robots carry `bindingRevision`. Test actor `executor` was added.
- Contracts: a `RobotManifest` definition in `wire.schema.json` (RobotManifest fields + optional `targetKind`, `units`, `frame`, `footprint{widthM,lengthM}`, `speedControl`, `maxSpeedMps`, `zoneEnforcement`, `docking`). The `robot-manifest.schema.json` wrapper (`mekoniq.robot-manifest.v1`) points at it. Also added: generated `wire.ts`, `validateRobotManifest`, and `robot-adapters` `RobotManifest` re-exported from the generated type, plus a Python schema test.
- Tablet: `apps/tablet-web/src/screens/RobotSetup.ts`, route `/robot-setup` (`robot.configure`), nav entry, VI/EN.
  - For each robot it shows the profile reason, the map the robot reports and the binding epoch, admission reasons per capability, and each point's binding status (current / stale / not taught).
  - It has a bind form with required units and frame (yaw in radians). `robotSetupView` is the pure view under test.
- Lab (R-W06-T01): in `restaurant-lab`, a partial seed of the fixture robot `sim-1` merges the fixture defaults. The fixture robot now carries `bindingRevision:'1'` (= `mapRevision`), `speedControl`, `zoneEnforcement:false` and a footprint.

## Limits

- Every robot in these tests is simulated or a seeded profile. The registry entries for `ros2`/`valetudo` are caps, not proof. Each real model still needs its versioned manifest and hardware evidence (W06-T02..T04), and the venue still needs commissioning.
- The executor's report of a new map revision is modelled by the robot snapshot (seeded in tests). Reporting it from a real adapter belongs to W06-T02/T03. `dispatchRobotEffects` still refuses non-simulated manifests (`NATIVE_EXECUTOR_REQUIRED`).
- Zones are named resources that the executor reserves before entering. Deriving the zones a path crosses from map geometry is not done. A command's `limits` do not yet carry the mission speed limit.
- Admission of a mission does not require zone reservations; traffic is enforced by the executor's `Zone.Reserve` before movement.
