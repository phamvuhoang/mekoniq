# W09-T01 — Menu/config rollout per branch

Status: verified_local (software only; local Supabase PostgreSQL 17 + the real cloud modules). No tablet or hosted Supabase is exercised: a "venue acknowledgement" in the tests is the venue's synced accepted fact written into `sync_projection`, the same row the real sync path produces.

## What was built

- `supabase/migrations/20261104000100_chain_rollout.sql`: `chain_revision` (immutable chain snapshots), `chain_branch_override` (versioned per-branch overlay), `chain_rollout_target` (desired version per revision/branch/kind). Organisation-scoped RLS (`app.organization_id`), `mekoniq_app` has no delete. `withOrganization` (tenant-context.ts) binds only the organisation; per-venue facts are always read through `withTenant` one venue at a time, so a chain call never widens a venue scope.
- `packages/domain/src/chain/overlay.ts` (pure): `validatedOverride` (only `unitMinor`, `available`, `stationId`; unknown item / field / bad value refused), `overlayItems` (no mutation), `rolloutState(desired, effective, failedCode?)` → applied | pending | failed | superseded, `compareItems`.
- `apps/cloud-web/src/server/modules/chain/`: `catalog-rollout.ts` (`createChainRevision`, `rollBackForward`, `previewRollout`, `chainPublish` = Chain.Publish, `compareBranches`, `listChainRevisions`), `branch-overrides.ts`, `rollout-state.ts` (`rolloutStatus`, `venueEffective`, `requireChain`).
- Routes `/v1/chain/*` (permissions `chain.read` / `chain.publish`; owner `*` only — managers are branch-scoped and have neither). Page `/admin/chain/configuration` + `ChainConfiguration.tsx`.

## Behaviour

- Publishing never changes a branch: it records the desired version and relays the existing `Catalog.Publish` (and `publishConfiguration` for `features`). **Effective** is only what the branch itself synced (catalog `state.version`, newest applied configuration). Offline branch keeps `effective` until it acknowledges.
- Retry = calling publish again for the same revision: an applied branch is untouched; a relay still in flight (pending and unexpired, or `unknown`) is not duplicated; an expired or refused one gets a new attempt with a fresh operation id. The venue's own version check (`VERSION_CONFLICT`) makes a late duplicate harmless.
- A branch that cannot take the revision (e.g. the override or menu names a station it lacks) is recorded `failed` with a code (`STATION_NOT_FOUND`) and never blocks the others.
- Roll back forward = a new revision copied from an old snapshot (`restores`); revision numbers only increase. Accepted orders keep their frozen charge snapshots (unchanged W05 behaviour).
- Per-venue rights: every venue named in a call must grant `chain.publish`/`chain.read` to the actor; a missing venue or other organisation is `SCOPE_DENIED`.

- Re-dispatch of an expired relay happens when publish is called again; no scheduled job re-sends it yet.
- The tablet-side application is the existing `Catalog.Publish`/`Configuration.Apply` path; this task adds no new tablet command, and Gate A/B hardware evidence is untouched.
- The UI was type-checked and linted, not browser-tested.
