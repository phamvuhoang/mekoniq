# W09-T03 — Connector contract, online order ingress and effect receipts

Status: verified_local (local PostgreSQL 17 + the real cloud modules, route registry and job runner + the real domain registry in the restaurant lab). Channels are the **sandbox** simulator only; no real provider, marketplace or Zalo app is contacted and none is enabled.

## What was built

- `integrations/core/src/`: `webhook-signature.ts` (`v1=` HMAC-SHA256 over `${timestampMs}.${rawBody}`, constant-time compare, ±5 min replay window, signature checked before the clock), `external-ids.ts` (identity = provider + merchant + external id; canonical payload fingerprint; `classifyReceipt` new/duplicate/conflict), `connector.ts` (`Connector.normalize/execute/query`, profile registry — only sandbox profiles are enabled; `zalo-mini-app` and `delivery-marketplace` exist but are refused until a W10 certification), `inbox.ts` (forward-only status, hold/reject policy for a silent venue), `outbox.ts` (outcome → job state), `sandbox.ts` (simulator with timeout / lost-ack / 429 / refusal faults).
- Migration `20261104000300_external_orders.sql`: `channel_credential` (key id → exactly one tenant/venue/merchant, `hold`|`reject` policy; looked up through a definer function, secrets are **derived** from `CHANNEL_SECRET_MASTER`, not stored; missing master = nothing authenticates), `external_order` (+ unique `external_order_identity` on org/venue/provider/merchant/external id), `external_order_conflict` (quarantine). Tenant RLS on all three.
- Cloud (`server/modules/channels/`): `credentials.ts`, `ingress.ts` (`POST /v1/channels/:provider/webhooks` — a `raw` route: the registry hands over the exact bytes and does not parse; signature, then strict JSON, then normalisation that drops every channel-supplied price; merchant must equal the credential's; expiry must be in the future and ≤24 h), `restaurant-ack.ts` (`refreshFromVenue` reads the venue's relay receipt and synced `external-order` aggregate; `sweepExternalOrder`; `resolveDeadLetter`).
  - **202 `received` never means accepted.** `venueRecorded` turns true only when the venue's relay receipt is `accepted`; `status: accepted` only from the venue's own decision (its synced aggregate). A decision is never overwritten by a cloud timer; a contradiction (venue accepted after the cloud rejected/expired) is kept as `attention`.
  - Duplicate (same payload) → stored answer, one row, one relay. Same identity, different payload → `409 EXTERNAL_ORDER_PAYLOAD_CONFLICT`, content kept in `external_order_conflict`, original untouched.
  - Silent venue: `reject` policy answers `VENUE_UNAVAILABLE` after the relay window; `hold` re-relays with a fresh window until the order's own deadline, then expires (and asks the venue to expire it).
  - Relay: a new `channel:` source (`cloud-channel`) with only `ExternalOrder.Receive|Expire` and only `channel.ingest` at the venue (mirrors the guest relay).
  - Outbound: job types `channel.effect` (one job per order+kind, the job id is the channel's idempotency key; a thrown call is `unknown`, the next lease **queries first**; 429 and refusal retry, then `dead_letter`; only `channel.operate` retries/abandons) and `channel.sweep`.
- Domain (`orders/external.ts`, feature `online`): `ExternalOrder.Receive` (prices from our own menu, `AMOUNT_MISMATCH` against the declared total, refuses expired, payload-conflict; no order, no kitchen ticket), `Accept` (needs an open session; re-quotes and refuses `EXTERNAL_PRICE_CHANGED`; creates the order with `placeOrder` → `OrderAccepted`), `Reject`, `Expire` (never an accepted order). Permissions `channel.ingest` (relay only), `channel.accept` (cashier, manager), `channel.operate` (manager).
- Guest: `/order/[venueId]?o=<org>` + `OnlineCheckout.tsx`, labelled sandbox, polls the status and shows "received / accepted / rejected / expired" distinctly. Public route `POST /v1/channels/web-sandbox/:org/:venue/orders` is refused unless `CHANNELS_SANDBOX_WEB=1`, assigns the external id and merchant itself, tags `sandbox`, caps items (20) and open requests (20 → 429).

## Limits

- **Partial fulfilment is not supported**: an order is accepted whole or rejected whole (`ITEM_UNAVAILABLE`-type codes at Receive). Mapping an unavailable line to a partial acceptance needs a provider's own partial-fulfilment semantics (W10).
- The venue-side `ExternalOrder.*` handlers run in the TypeScript domain bundle; the real-tablet receipt/relay path for the new `channel:` source is exercised by the cloud relay code and the lab, **not** by a physical coordinator (Gate A device evidence is separate and unchanged).
- Real webhook schemas, merchant onboarding, certificates and provider retry semantics are W10; the sandbox profile's body shape is ours.
- The sweeper is scheduled as a `cloud_job` per order (first round 2 min after receipt); it depends on the existing job wake-up (Supabase Cron → `/internal/jobs`), not exercised against a hosted project.
- Accept needs a session chosen by staff (a counter/pickup table); there is no automatic table for online orders yet.
