# W08-T03 — Bookings, waitlist and deposits

Status: verified_local (software only; SQLite restaurant lab + build of the Next.js app). No payment gateway, SMS reminder or table-sensor is involved.

## What was built

- `packages/domain/src/reservations/`:
  - `resource.ts` `rangesOverlap` (the plan's function, touching ends do not overlap), the blocking rule (`blocks`: confirmed/checked-in always; a *requested* booking only while its hold is live **or while a deposit for it is pending/unknown** — an unknown payment never frees a table by itself; a provisional/isolated booking never blocks), `tableBusy`, and `touchCalendar`: every change that takes or frees a table also bumps `table-calendar/<table>`, because two racing bookings would otherwise create two different booking ids and both commit — with the shared row the store's version check lets exactly one win.
  - `booking.ts` `Booking.Create` (UTC instants only — naive local times are `INVALID_RANGE`; length ≤ 8 h; table known, seats respected, not in the past; `holdMinutes` default 15; `isolated:true` = provisional), `Booking.Confirm` (re-checks the calendar and that the required deposit is **paid in full across receipts**), `Booking.CheckIn` (from `earlyMinutes` before start to the end of the slot, onto a free table, opens the table session in the same shape as `Session.Open`, records `lateMs`), `Booking.NoShow` (only after start + grace, reason required; optional forfeit only if policy `noShowForfeit` and the actor has `deposit.manage`), `Booking.Cancel`.
  - `deposit.ts` `Deposit.Receive` (cash goes through the open shift's drawer as a `cash-movement` in — visible to the cashbook and shift report, **not** sales; transfer needs a reference; `pending`/`unknown` are real states resolved by sending the same deposit as `paid`/`failed`), `Deposit.Apply` (a tender on a prepared bill: payment method `deposit`, one application per deposit+bill, bounded by the bill's due and the deposit's liability, revenue still recognised once when the bill closes), `Deposit.Return` (manager `deposit.manage`; never more than the liability; cash leaves the drawer of the shift that took it and only what the drawer holds). Liability = paid − applied − returned − forfeited.
  - `waitlist.ts` `Waitlist.Join`, `Waitlist.Promote` (capacity first, then first-come-first-served among the parties the table fits — leaving an earlier party behind needs a recorded `skipReason`; the table must be free now for the whole stay; creates a confirmed booking so the slot is taken).
  - Policy `reservation-policy/current` {graceMinutes 15, earlyMinutes 30, noShowForfeit false}.
- Permissions: `reservation.write` (cashier, manager) for bookings/waitlist/deposit receive+apply; `deposit.manage` (manager) for returning and forfeiting (`Booking.NoShow` with `forfeitDeposit:true` needs both, added in `requiredPermissions`). Feature `reservations`.
- Cloud: allowlist `Booking.Create/Confirm/Cancel`, `Waitlist.Join`; readable `booking`, `waitlist`, `deposit` (need `reservation.write`); page `/admin/reservations` (`Reservations.tsx`) whose request text states plainly that the table is **not guaranteed** until the venue's own calendar confirms (cloud bookings carry `channel:'cloud'` and stay `requested`).
- Tablet: `Reservations.ts` at `/reservations`: bookings by time with confirm / check-in / no-show (reason) / cancel / take cash deposit, outstanding deposits as a labelled liability with manager return, waitlist with position and seating, create form; a booking made while the session mode is `isolated` is sent `isolated:true` and shown as provisional. `LanService.kt` lets the till role read `booking`, `deposit`, `deposit-application`, `waitlist`.

## Limits

- Table-merge dependency (W05 session merge) is not modelled: a booking is for one table; booking a merged set of tables is not supported yet.
- The tablet can only *create* an isolated booking while disconnected; the venue's owner re-checks it at confirm time. There is no automatic conflict resolution UI beyond `TABLE_UNAVAILABLE` at confirm.
- Deposits by card terminal / payment provider and refunds of a `deposit`-method bill payment are not built: `Refund.Record` on such a payment is refused (`INVALID_METHOD`); return money through `Deposit.Return` before applying, or refund the bill's other tender.
- Business-date / timezone handling is by UTC instants end to end (the tablet form converts local time to UTC); there is no per-day capacity report.
- The cloud request flow was type-checked and built, not exercised in a browser.
