# W07-T02 — Suppliers, purchasing, receiving, returns and ingredient cost

Status: verified_local (software only; SQLite restaurant lab). No supplier integration, scanner or accounting system is claimed.

## What was built

- `packages/domain/src/procurement/`:
  - `supplier.ts` `Supplier.Upsert`.
  - `purchase-order.ts` `Purchase.Create` (draft; quantities frozen in base units, price per *ordering* unit with `perBase`; supplier/ingredient currency must match), `Purchase.Approve` (only an approved order can be received; per-line **tolerance** is set here), `Purchase.Close` (short-close with a reason; receipts already booked stay), and `receivable(ordered, received, tolerance)` exactly as the plan states.
  - `goods-receipt.ts` `Goods.Receive` (single-line shorthand or `lines[]`): receipt id is content-addressed from **supplier + delivery-note number**; the same note with the same lines is a no-op, with other lines `SUPPLIER_RECEIPT_REUSED`. Takes only what the order still allows (`OVER_RECEIVED`), `PURCHASE_NOT_RECEIVABLE` for draft/closed/fully received orders, `CURRENCY_MISMATCH`, exact unit conversion (`UOM_CONVERSION_MISSING`). In the same commit it appends a `receipt` stock movement per line and raises the item's `onHand` and `valueMinor` (moving weighted average: value joins the stock, integer arithmetic, rounded half up).
  - `return.ts` `Goods.Return {sourceEventId, receiptId, ingredientId, quantity, reason}`: leaves at the value that **receipt** brought in (not today's average), never more than the receipt delivered (`RETURN_EXCEEDS_RECEIPT`), idempotent on `sourceEventId`, writes a `return` movement and records `returned` on both the receipt line and the PO line. Returning does not reopen the order.
  - `cost.ts` `lineValue`.
- Permissions: `procurement.write` (supplier, create), `procurement.approve` (approve, close), `procurement.receive` (receive, return) — manager only (owner `*`); a chef gets `FORBIDDEN`. Feature `procurement` (depends on `inventory`): supplier/create are *new* work, the rest `finish_existing`.
- UI `apps/tablet-web/src/screens/Purchasing.ts` at `/purchasing` (Manage page): PO list with received/ordered/returned, create (`ingredient qty unit cost` lines), approve, receive partial, close, return from a receipt, add supplier. The tablet works from the coordinator's snapshots, so it needs no Next.js. Accounts payable is out of scope: nothing here posts to a ledger beyond stock value.
- Fixtures: `procurement` enabled; `supplier-1`; approved `po-1` (5 000 g of rice-raw at 20 minor/g).

## Limits

- **Offline receipt reconciliation** is covered by the shared mechanisms (the content-addressed receipt id makes the same delivery note from two tablets collide on sync and resolve through the existing conflict path, W04), but this task has no separate partition test; the receive commands themselves are the same ones a tablet runs offline.
- Receiving into an already negative balance books the received value in full (the negative quantity carries no value), so the average cost after such a receipt is value / (new on-hand).
- Cost is weighted average only (no FIFO layers). Returns use the receipt's average line cost; returning stock that has since been consumed can leave a small residual value or zero it (value is floored at 0).
- Payable summary export is not built (no accounting claim); the receipt/PO aggregates carry the data for it.
