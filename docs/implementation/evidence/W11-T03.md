# W11-T03 — Backup, migration and restore with old clients offline

Status: **blocked_external** — the backup, verification, restore-rehearsal and expand/contract tooling is implemented and exercised on the local Supabase database; production recovery (measured RPO ≤ 5 min / RTO ≤ 30 min), an independent encrypted target and a platform-level Auth restore have not been done.

## What was built

- `scripts/backup-restore-lib.mjs` (`createBackup`, `restoreInto`, `neutralizeLiveEffects`, `verifyRestore`), `scripts/backup-verify.mjs` (`verifyBackup`), `scripts/restore-rehearsal.mjs`, `scripts/export-storage.mjs` (`exportStorage`: manifest + verified object copies), `scripts/migrate-release.mjs` (`migrationAllowed`, `classifyMigration`, `planMigrations`, `--plan`/`--clearance`), `deploy/profiles/backup-policy.json` (declared, `not_configured`).
- `tests/integration/upgrade-recovery.test.ts` (6 tests), `docs/operations/{backup-restore,rolling-upgrade}.md`; `setupWave02` can target a scratch database (`MEKONIQ_TEST_DB`).
- Restore details learned the hard way and handled: the dump's `CREATE SCHEMA public` needs the empty schema dropped first, provider-role `ALTER DEFAULT PRIVILEGES` lines cannot be applied by a non-superuser and are the platform's anyway, and a re-created `public` must be granted usage to PUBLIC or the app role cannot see its tables.

Cases: **an offline tablet's cash receipt written after the checkpoint syncs into a cloud restored from that checkpoint and upgraded with a new migration, twice, landing once** (the source database is untouched); a restore matches its backup (row counts, forced RLS, app role) and Auth ids/memberships survive; pending relay commands are expired and in-flight jobs become `unknown` after a restore; a removed receipt row is detected; backup verification catches corruption, a missing segment, a stray file, a missing/corrupt Storage object, credentials in the Auth inventory and a missing manifest; Storage export refuses a damaged object; `migrationAllowed` truth table, destructive statements classified (comments ignored), CLI exit codes; the shipped migrations are expand-only; the declared policy is honest.

## Limits (why blocked_external)

- **No production RPO/RTO.** A local rehearsal on a developer machine measures nothing about the real project; a Free project has no PITR. The drill on the real project, the monthly schedule and the cost are the operator's.
- No independent, encrypted off-site target exists (`target.chosen: null`); encryption and key custody are specified, not exercised.
- Auth: only an inventory (ids/emails) is restored into a stub; real password/session restoration and login after restore belong to the platform and were not exercised. Storage: object copies are tested with a fake downloader, not against Supabase Storage.
- The restore targets a scratch database on the same local server through its container; the production procedure uses the same steps with the real connection and tooling.
- O19 and O22 (late import dedup, old-client sync across restore) are covered by the first test and by the existing archive/continuity tests; a native Android export/import with device epochs and key recovery was not exercised.
