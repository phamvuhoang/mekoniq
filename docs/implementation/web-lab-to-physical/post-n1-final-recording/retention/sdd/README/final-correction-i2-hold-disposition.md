# I2 completed-hold consistency clarification

Ruling: when an initially authorized existing-run reclaim hold completes after the requester expires, synchronize only the existing entry readOnly safety state with the already-held runner, while preserving owner/readers and monotonic durable epoch and refusing the expired requester response/ownership — the hold cannot be rolled back into a resumable physical state and an entry still advertising writable control would be inconsistent — if wrong, a previously writable owner may be restricted after a request that ultimately failed; deterministic tests must prove authorized hold admission, 401/no locked-input publication for the expired caller, no new read/owner grant, owner reconcile-only behavior and no resume/motion. This is within I2, not a second fix wave.

Implementer discovered this during self-review of an existing writable runner: holdForReclaim can durably mark the runner reclaimed before session expiry is observed on return. Merely preserving entry.readOnly:false misrepresents its control state. Existing owner/readers must remain; a successful hold must be represented conservatively, never undone to satisfy a failed request. New/cold handles remain owned cleanup on refusal.
